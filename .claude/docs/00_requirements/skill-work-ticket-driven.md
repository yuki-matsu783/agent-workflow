# チケット駆動ワークフロースキル

## 概要

Claude Code の作業を「計画 → チケット化 → 1枚ずつ実施 → 記録」という流れに統一し、フェーズに応じたツール利用制限をフックで強制するためのスキルの要件を定義する。

- **背景**: Claude Code に作業を依頼すると、調査のつもりがコードを書き換えてしまう、作業の途中経過が残らない、といった問題が起きうる。作業をチケット単位に分割し、フェーズごとに許可される操作をフック（PreToolUse / PostToolUse）で機械的に強制することで、意図しない変更を防ぎ、作業履歴を残したい。
- **目的**: 「調査・実装・振り返り」の各フェーズで許可された操作だけが実行されることを保証し、各チケットに作業ログ（うまくいったこと・いかなかったこと）が記録される状態を実現する。
- **スコープ**:
  - 含む: スキル本体（SKILL.md）、チケット/計画書/結果報告のテンプレート、PreToolUse / PostToolUse フックスクリプト、`.claude/settings.json` へのフック登録
  - 含まない: CI/CD との連携、リモートリポジトリへの push 運用、複数人での同時作業

---

## ユーザーストーリー

**[As a]** Claude Code を使って開発する開発者として、

**[I want]** 作業をチケット単位で計画・実行させ、フェーズごとに許可された操作だけが行われるようフックで強制したい。

**[So that]** 調査中の意図しないファイル変更を防ぎ、各作業の経過と学びをチケットに記録として残すため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When スキルが起動されたとき、Shall 計画（plan）を行い、調査・実装・振り返りの各タスクチケットを `wip/10_tickets/00_todo/` に作成しなければならない。
- When チケットの作業を開始するとき、Shall チケットを `wip/10_tickets/00_todo/` から `wip/10_tickets/10_doing/` に移動し、その時点でコミットを作成して差分チェックの基準点としなければならない。
- When チケットの作業中、Shall うまくいったこと・うまくいかなかったことをチケットの作業ログ欄に記録しなければならない。
- When チケットの完了条件を満たしたとき、Shall チケットを `wip/10_tickets/20_done/` に移動し、基準点からの差分が許可パスの範囲内であることを確認した上でコミットを作成しなければならない。
- When 全チケットが `done` になったとき、Shall 作業全体の完了をユーザーに報告しなければならない。

### 振り返り（retrospective）の棚卸しと合意

`workflow-quick-request`（軽作業ワークフロー）手順5と観点・文言を揃え、2つの振り返りの入口で形式を統一する（issue #3）。

- When retrospective チケットを実施するとき、Shall 結果報告の作成に加えて、使った AI アセット（スキル / フック / ルール / エージェント / CLAUDE.md の5種類）を棚卸ししなければならない。
- When 棚卸ししたアセットを振り返るとき、Shall 各アセットについて 足りなかった / 邪魔だった / 無かった / 問題なし の4観点のいずれかで気付きを述べなければならない。
- When 振り返りから修正・新規作成の候補が挙がったとき、Shall 候補を 軽微（続けて修正）/ 振る舞いが変わる（新規issueを作って`workflow-issue-mr-driven`で進める）の2区分に分け、`AskUserQuestion` でユーザーの合意を得なければならない。候補が無いときも「候補なし」として確認しなければならない。

### フェーズ判定（状態ソース）

- When フックがフェーズを判定するとき、Shall `wip/10_tickets/10_doing/` にあるチケットのフロントマター（`type` / `status`）を唯一の状態ソースとして参照しなければならない。

### フックによる強制（調査フェーズの例）

- When 調査チケット（`type: investigation`）が doing にある状態で禁止パス（deny）への Edit/Write が試行されたとき、Shall PreToolUse フックは exit 2 で拒否し、理由を stderr に出力しなければならない。
- When 作業タイプの定義に記載のないパスへの Edit/Write が試行されたとき、Shall PreToolUse フックは「本来想定していないパスを触ろうとしている」旨の警告を添えてユーザーに確認を求めなければならない（拒否ではなく確認）。
- When ユーザーが確認で承認したとき、Shall フックはそのパスの親ディレクトリ（設定で指定した特別なファイルはファイル単位）をセッション内で記憶し、同じセッション中は再確認してはならない。
- When 毎回確認が必要と定義されたパス（ask）への Edit/Write が試行されたとき、Shall PreToolUse フックは承認履歴に関わらず毎回ユーザーに確認を求めなければならない。
- When 調査チケットが doing にある状態で読み取り系以外の Bash コマンドが試行されたとき、Shall PreToolUse フックは deny-by-default で拒否しなければならない。
- When ツール実行後に許可パス以外への差分（未追跡ファイルを含む）が検出されたとき、Shall PostToolUse フックは additionalContext で差分の存在と復旧指示を Claude に伝えなければならない。
- When チケットが doing にある状態でプランモード（EnterPlanMode）が試行されたとき、Shall PreToolUse フックは exit 2 で拒否しなければならない（プランモードはワークフロー開始時の全体計画の作成・合意にのみ使用する）。
- When チケット作業中に `.claude/` 配下（settings.json・フック・スキル・設計ドキュメント）への書き込みが試行されたとき、Shall フックはチケットの `allowed_paths` の指定に関わらず拒否しなければならない（保護パス）。ただし、作業タイプ定義でそのパスを許可された作業タイプ（例: `ai-asset-design` は `.claude/docs/` のみ、`ai-asset-implementation` はフック・ルール・スキル・settings.json）のチケットでは許可する。

### 作業タイプの拡張性

- When 作業タイプとパス（ディレクトリまたはファイル単位）の allow（触ってよい）/ deny（触ってはならない）/ ask（毎回確認）の対応を定義・変更するとき、Shall フックのコードではなく外部設定ファイル（JSON）で行え、フックはそれを動的に読み込んで適用しなければならない。
- When チケットのフロントマターに `allowed_paths` が指定されたとき、Shall フックはそれを確認なしで書き込めるパスとして追加で扱う。ただし deny / ask の定義に優先してはならない。
- If 外部設定ファイルが存在しない・解釈できない場合、Then フックは安全側に倒して書き込み系操作をブロックし、設定ファイルの修正のための編集だけを許可しなければならない。
- When doing チケットの frontmatter `type` を書き換える編集が試行されたとき、Shall PreToolUse フックは拒否しなければならない（作業タイプの自己変更による制限の無効化を防ぐ）。作業ログなど `type` 以外の編集は許可する。

### 外部ツール依存のフォールバック（gh CLI 不在時）

`work-boundary.sh`（ワーク境界のレビュー往復）と `merge-prep.sh`（マージ前作業）は GitHub 操作に `gh` CLI を用いる。GitHub 操作が MCP サーバー経由に限定され `gh` CLI が使えない実行環境でも、これらのスクリプトが機能停止しないことを要件とする（issue #41）。

- When `gh` CLI が利用できない実行環境で `work-boundary.sh`/`merge-prep.sh` の各サブコマンドが呼ばれたとき、Shall スクリプトは `gh` を自ら呼び出す代わりに、呼び出し元（Claude）が MCP ツール等で取得・実行した結果（PR 番号、コメント URL、レビュー判定など）を引数として受け取り、前提条件の検証と状態ファイルへの記録を行わなければならない。
- When `gh` CLI が利用できる実行環境のとき、Shall 既存の自動実行（`gh` を自ら呼び出す挙動）を変更してはならない（後方互換）。
- When フォールバック経路（呼び出し元からの値の受け取り）を用いたとき、Shall 状態ファイルに記録の経路（`gh` 自身が確認したか、呼び出し元から渡された値か）を残さなければならない。フォールバック経路は、スクリプト自身が GitHub に問い合わせて真偽を確認する現在の証跡強度（LLM の自己申告だけでは状態が進まない設計）を維持できない。この強度低下の内容と許容範囲を仕様書に明記する。
- When `merge-prep.sh` の `reset-wip`/`check-conflicts` が呼ばれたとき、Shall PR 番号の取得元を `gh pr view` に限定せず、呼び出し元からの明示指定でも動作しなければならない（この2つは PR 番号の特定以外に `gh` を必要としない）。

### マージ進行中の保護ファイル編集（issue #51）

`workflow-boundary.sh` の WF012 は `wip/10_tickets/review-state.json` と `wip/merge-prep.json` への直接書き換えを常時拒否する（`work-boundary.sh`/`merge-prep.sh` 経由の更新のみを正としてきた）。マージコンフリクト解消時にこの2ファイル自身がコンフリクトを起こすと、常時拒否のままでは Claude が解消できず作業が止まる。マージ進行中に限りこの拒否を解除できることを要件とする（issue #51）。

- When `git` が実際にマージ進行中（`MERGE_HEAD` が存在する）かつ対象ファイル自身が unmerged 状態（`git diff --name-only --diff-filter=U` に含まれる）の両方を満たすとき、Shall WF012 は Edit/Write および Bash による直接書き換えを拒否してはならない（例外的に許可する）。
- If 上記の両方の条件を満たさない場合（マージ進行中でない、または対象ファイルが unmerged でない場合を含む）、Then WF012 は現行どおり常時拒否しなければならない（`MERGE_HEAD` の単純な存在チェックのみでは doing 空の状態で偽装され得るため、対象ファイル自身の unmerged 状態も併せて確認する）。
- When 例外が適用され編集が行われた後、Shall PostToolUse フックは編集後の内容を検証し、有効な JSON でない・コンフリクトマーカーが残っている・対象ファイルが unmerged のままである、のいずれかに該当する場合は additionalContext で警告しなければならない（自動 revert は行わない）。

### アルタナティブフロー（代替経路）

- If `wip/10_tickets/10_doing/` にチケットが存在しない場合、Then フックは何もせず exit 0 で終了しなければならない（通常セッションへの影響ゼロ）。
- If 環境変数 `WORKFLOW_ENFORCE=0` が設定されている場合、Then フックはすべてのチェックをスキップしなければならない（緊急脱出用）。
- When セッションが中断後に再開されたとき、Shall スキルは `wip/` 配下の状態を確認し、doing のチケットがあればそこから作業を再開しなければならない（冪等性）。
- When retrospective の振り返り合意で「issue を作って `workflow-issue-mr-driven` で進める」が選ばれたとき、Shall `workflow-issue-mr-driven` の完了処理（マージ前作業・draft 解除）が終わった後に、同スキルを読み込んで手順1から新しい issue の作業を開始しなければならない。

### 例外フロー（エラーケース）

- If `wip/10_tickets/10_doing/` に2枚以上のチケットが存在する場合、Then フックは異常状態としてツール実行をブロックしなければならない（WIP リミット = 1 の強制）。
- If doing チケットのフロントマターが読み取れない・`type` が不正な場合、Then フックは安全側に倒して書き込み系操作をブロックし、理由を出力しなければならない。
- When フックが操作を拒否したとき、Shall not フックは作業ツリーへの自動 revert（`git checkout --` 等の破壊的操作）を行ってはならない。復旧は additionalContext による指示を受けた Claude が行う。

## 前提条件

- 対象プロジェクトが Git リポジトリであること。
- `wip/` ディレクトリ配下（`wip/10_tickets/00_todo|doing|done`、`wip/20_plans`、`wip/30_reports`）が作業領域として利用できること。
- 作業は main 以外の作業ブランチ上で行われること。

---

## 制約条件

- **技術的制約**: フックは Windows（Git Bash）環境で動作すること。ステートレスなシェルスクリプトであるため、フェーズ判定に必要な情報はすべてファイル（doing チケットのフロントマター）から取得すること。
- **ビジネス的制約**: 特になし。
- **外部的制約**: Claude Code のフック仕様（PreToolUse は exit 2 + stderr でブロック、PostToolUse は additionalContext で文脈追加）に準拠すること。

---

## 依存関係

- Claude Code のフック機構（`.claude/settings.json` への登録）
- Git（基準点コミット・差分検出に使用）
- 仕様の詳細は `.claude/docs/10_spec/skill-work-ticket-driven.md`（フェーズ×許可マトリクスを含む）で定義する

---

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | フックは全ツール呼び出しで発火するため、ガード条件（doing 不在なら即 exit 0）を先頭で評価し、通常セッションのオーバーヘッドを最小にすること |
| セキュリティ | フックが拒否理由を出力する際、機密情報を含めないこと |
| 可用性 | `WORKFLOW_ENFORCE=0` による無効化手段を常に確保し、フックの不具合が作業全体を止めないようにすること |
| テスト容易性 | フックは stdin に JSON を与えて exit code を検証するユニットテストが可能な構造にし、判定結果をログファイルに残すこと |
