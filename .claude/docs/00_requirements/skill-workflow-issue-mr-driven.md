# issue-PR 駆動ワークフロースキル

## 概要

ユーザーの依頼を GitHub の issue と PR（MR）に紐づけてから実作業に入る、開発の振り分けとなるワークフローの要件を定義する。実作業そのものはチケット駆動ワークフロー（`.claude/docs/00_requirements/skill-work-ticket-driven.md`）に委ねる。

- **背景**: チケット駆動ワークフローは作業ブランチ上での「調査 → 実装 → 振り返り」を統制するが、**その作業が何の issue に対するもので、どの PR に載るのか**は扱っていない。依頼のたびに Claude が独自の判断で作業を始めると、既存 issue と重複した対応や、issue に紐づかない PR が生まれる。作業の起点を issue に固定し、issue の確定には必ず人間の承認を挟みたい。
- **目的**: 「依頼 → 既存 issue の照合 → 人間の承認 → issue の確定（作成 / 修正）→ feature ブランチと draft PR の作成 → チケット駆動ワークフロー」という順序を固定し、すべての作業が 1 つの issue と 1 つの PR に紐づいた状態を実現する。
- **スコープ**:
  - 含む: スキル本体（SKILL.md）、issue 追記用テンプレート、issue コメント用テンプレート、類似 issue の判定基準、既存スキル（task-gh-issue / task-gh-feature / work-ticket-driven）との連携仕様、完了処理（マージ前作業と draft 解除）の順序と承認
  - 含まない: PR のマージ（人間が行う）、レビューの自動化、GitHub 以外のホスティング（GitLab の MR など）、`Closes #N` 以外の関連 issue の自動特定（追加の通知先は人間が指定する）。ワーク境界・マージ前作業の判定スクリプトとフックの仕様は `.claude/docs/10_spec/skill-work-ticket-driven.md` が正

---

## ユーザーストーリー

**[As a]** Claude Code を使って開発する開発者として、

**[I want]** 依頼した作業を、既存 issue との照合と自分の承認を経て issue と PR に紐づけた上で、チケット駆動で進めてほしい。

**[So that]** 重複した対応や issue に紐づかない変更を防ぎ、依頼・合意・作業・成果の経緯を GitHub 上で追えるようにするため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When ユーザーから作業の依頼を受けたとき、Shall スキルは実作業を始める前に依頼を要約し、既存の issue（open を優先、必要に応じて closed も）を検索して類似候補を提示しなければならない。
- When 類似する issue が見つかったとき、Shall スキルはその issue で対応するかどうかをユーザーに確認し、承認を得るまで issue の変更・ブランチ作成・実作業を行ってはならない。
- When 既存 issue で対応することが承認されたとき、Shall スキルは今回の依頼内容と受け入れ条件を issue に追記する案を提示し、承認後に task-gh-issue スキルで issue を修正しなければならない。
- When 類似する issue が見つからなかったとき、Shall スキルは新しい issue の案（タイトル・種別・概要・受け入れ条件）を提示し、承認後に task-gh-issue スキルで issue を作成しなければならない。
- When issue が確定したとき、Shall スキルは task-gh-feature スキルで issue 番号を含む feature ブランチと、issue に紐づく（`Closes #N`）draft PR を作成しなければならない。
- When ブランチと PR が作成されたとき、Shall スキルは issue 番号・PR の URL・issue の受け入れ条件を引き継いでチケット駆動ワークフローを開始しなければならない。
- When チケット駆動ワークフローの1つのワーク（同じ作業タイプのチケット群）が完了したとき、Shall スキルは作業ブランチを push し、PR の本文にそのワークの要約を追記し、PR 上でレビューを依頼して、レビュー完了の連絡を受けるまで次のワークに着手してはならない。
- When レビュー完了の連絡を受けたとき、Shall スキルは PR のレビュー・コメント（会話タブおよびインライン）を取得して提示し、対応が必要な指摘があれば同じ作業タイプの追加チケットとしてチケット駆動ワークフローに再実行させなければならない（完了済みチケットを未完了に戻さない）。
- When 全チケットが完了したとき、Shall スキルは PR の本文を成果（変更内容・動作確認・振り返りの要約）で最終的に更新しなければならない。
- When PR 本文を最終更新し draft を解除する前に、Shall スキルはマージ前作業として、`wip/` 配下の成果物（チケット・計画・報告・レビュー状態）のリセット、default ブランチとのコンフリクト確認（あれば解消）、関連 issue（`Closes #N`）へのコメント投稿を行い、それらが実施済みであることをスクリプト（`merge-prep.sh`）の記録と再検証によって機械的に確認しなければならない。
- When マージ前作業がすべて記録され再検証を通ったとき、Shall スキルは `merge-prep.sh ready` で draft を解除してマージを依頼し、マージ自体は行わず人間に委ねなければならない。

### 承認ポイント

- When 「どの issue で対応するか（既存 / 新規）」を決めるとき、Shall スキルはユーザーの明示的な承認を得なければならない。
- When issue に書く内容（新規本文 / 追記）を確定するとき、Shall スキルはユーザーの明示的な承認を得なければならない。
- When draft PR をレビュー可能（ready for review）に変更するとき、Shall スキルはマージ前作業に進む前にユーザーの明示的な承認を得なければならない。
- When default ブランチとのコンフリクトを解消するとき、Shall スキルは衝突内容を提示してユーザーの承認を得てから取り込み（`git merge`）を行い、履歴を書き換える方法（`git rebase`）を使ってはならない。
- When 関連 issue にコメントを投稿するとき、Shall スキルは投稿先と本文そのものを提示してユーザーの明示的な承認を得なければならない（他人の issue への投稿は取り消せない外部への副作用のため）。
- When ワーク完了のレビューを依頼したとき、Shall スキルは応答を終えて人間のレビューを待ち、`AskUserQuestion` でセッションを塞いではならない（ヘッドレス実行では応答が得られないため）。レビュー結果への対応要否の確認には `AskUserQuestion` を使ってよい。
- When 承認を求めるとき、Shall スキルは選択肢（例: 既存 issue で対応 / 新規作成 / 別の候補）を提示し、ユーザーが修正を加えられる形にしなければならない。

### 既存スキル・フックとの整合

- When issue を検索・作成・修正するとき、Shall スキルは自前で `gh issue` を組み立てず task-gh-issue スキルの手順に従わなければならない。
- When ブランチと PR を作成するとき、Shall スキルは task-gh-feature スキルの手順に従わなければならない。
- When チケット駆動ワークフローの実施中（`wip/10_tickets/10_doing/` にチケットがある間）であるとき、Shall not スキルは `gh` コマンドや `git push` を実行してはならない（フックの Bash allowlist で WF003 としてブロックされる。GitHub 操作は doing が空のときにのみ行う）。
- When 既存 issue の本文を修正するとき、Shall not スキルは既存の記述を削除・書き換えてはならない（末尾への追記のみ）。
- When draft を解除するとき、Shall not スキルは `gh pr ready` を直接実行してはならない（フックが WF015 で拒否する。`merge-prep.sh ready` 経由のみ）。
- When マージ前作業の状態（`wip/merge-prep.json`）を進めたいとき、Shall not スキルはファイルを直接編集してはならない（フックが WF012 で拒否する）。

### アルタナティブフロー（代替経路）

- If 現在のブランチに open な PR が紐づいており、かつ `wip/10_tickets/` にチケットが存在する場合、Then スキルは issue の照合からやり直さず、チケット駆動ワークフローの再開に進まなければならない（冪等性）。
- If 類似候補が closed な issue のみである場合、Then スキルはその issue を再オープンして対応するか、新規 issue を作るかをユーザーに確認しなければならない。
- If 依頼が複数の独立した問題を含む場合、Then スキルは issue を分割する案を提示し、ユーザーが選んだ 1 つから着手しなければならない（1 issue = 1 PR = 1 ワークフロー）。
- If ユーザーが issue 番号やissueやMRのURLなどを指定して依頼した場合、Then スキルは検索を省略してその issue を「既存 issue あり」として扱ってよい。
- If 依頼が `workflow-quick-request` の振り返り（手順 5-3）から「issue を作って workflow-issue-mr-driven で進める」と合意して切り替えて来たものである場合、Then スキルは引き継がれた summary / acceptance / kind / チケット構成（`ai-asset-design` → `ai-asset-implementation`）をそのまま用い、依頼の要約に関する曖昧点の質問を省略してよい。ただし未コミットの変更の確認は省略してはならない。

### 例外フロー（エラーケース）

- If `gh` が未インストール・未認証である場合、Then スキルは task-gh-install スキルまたは `gh auth login` を案内し、作業を開始してはならない。
- If 作業ツリーに未コミットの変更がある場合、Then スキルはブランチ作成前にユーザーへ扱い（コミット / stash / 破棄）を確認しなければならない（task-gh-feature の前提条件）。
- If PR 作成が「ベースブランチとの差分なし」で失敗した場合、Then スキルは空コミットを作成して再試行しなければならない。
- If issue の修正・PR の作成に失敗した場合、Then スキルは失敗したコマンドと出力をユーザーに報告し、勝手に別の手段で代替してはならない。
- If マージ前作業の前提が満たせない場合（todo にチケットが残っている・最後のワークのレビューが未完了・default ブランチと衝突している・通知先が無い等）、Then スキルは `merge-prep.sh` が返す未充足（WF016）を報告し、状態ファイルを直接編集して通そうとしてはならない。

---

## 前提条件

- 対象プロジェクトが GitHub 上の Git リポジトリで、`origin` が GitHub を指していること。
- `gh` CLI がインストール・認証済みで、issue と PR の作成権限があること。
- チケット駆動ワークフロー（スキル・フック・テンプレート）が導入済みであること。

---

## 制約条件

- **技術的制約**: GitHub（`gh` CLI）を前提とする。用語として「MR」は PR と同義に扱う。
- **ビジネス的制約**: 特になし。
- **外部的制約**: チケット駆動ワークフローのフック（Bash allowlist）に従うこと。フック側に GitHub 操作の許可を追加しない（統制の境界を変えない）。

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | issue 検索は `--limit` を付け、候補提示は上位 10 件程度に絞る |
| セキュリティ | issue / PR の本文に環境変数の値・トークン・個人情報を書かない |
| 可用性 | GitHub に接続できない場合でも、依頼の要約と issue 案の作成（ローカル）までは進められること |
| 追跡性 | ブランチ名・PR 本文・全体計画・結果報告のすべてに issue 番号を残す |
