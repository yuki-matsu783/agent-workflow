# スキル体系（workflow/work/task）要件定義

> 本文書は特定の1スキルに1:1で紐づく要件/仕様ではなく、複数スキルが参照する横断的なメタ文書である。

## 概要

- **背景**: `.claude/skills/` 配下のスキルは現在フラットに並んでおり、名前だけでは「どの粒度の作業か」「人間の承認が要るか」「他のワークフローから呼び出される部品か、それとも作業の振り分けか」が判別できない。改名前の `issue-pr-driven-workflow`（現 `workflow-issue-mr-driven`）と `gh-issue`（現 `task-gh-issue`）は見た目上対等だったが、前者は依頼を受けて人間承認を取りながら進める振り分け、後者は前者から機械的に呼ばれる部品であり、役割はまったく異なる。
- **目的**: スキルを役割・承認方式に応じて **ワークフロー（`workflow-*`）/ ワーク（`work-*`）/ タスク（`task-*`）** の3層に分類し、命名 prefix から粒度と承認方式が一意に読み取れる状態にする。
- **スコープ**:
  - 含む: 既存スキルの3層への分類と命名変更、命名規則・承認ルールの仕様化、フック・ドキュメントの参照更新
  - 含まない: 敵対的レビューエージェントを自動起動する具体的な実装（次段階の課題とする）。ワーク完了時のチェックポイントは「位置と入出力」のみ仕様化し、起動ロジックは対象外とする

---

## ユーザーストーリー

**[As a]** Claude Code のスキル・フックを保守する開発者として、

**[I want]** スキルの命名 prefix から「粒度」「承認方式」を一目で判別できるようにしたい。

**[So that]** 新しいスキルを追加・変更する際に、既存のどのスキルと同じ層に属するか、どんな承認フローを持たせるべきかを迷わず判断できるため。

---

## 受け入れ基準（Acceptance Criteria）

### 分類基準

- When スキルがワーク（`work-*`）の組み合わせで実現され、ワーク間に必ず人間承認（MRレビュー または AskUserQuestion）を伴うとき、Shall そのスキルは `workflow-*` に分類しなければならない。
- When スキルがタスク（`task-*`）の組み合わせ、またはチケット等のタスク相当の実行単位の組み合わせで実現され、人間の明示的承認なしに進み、複数タスク完了時点のチェックポイントで敵対的レビューエージェントの承認を伴うとき、Shall そのスキルは `work-*` に分類しなければならない。
- When スキルが作業実行者自身のセルフレビューで完結する作業レベルの手順であるとき、Shall そのスキルは `task-*` に分類しなければならない。

### リネームと参照の整合

- When 既存スキルを新しい命名 prefix にリネームするとき、Shall ディレクトリ名・`SKILL.md` の `name:`・リポジトリ内の全参照（フック、`CLAUDE.md`、仕様書、他スキルの本文、`evals.json`）を新名称に統一しなければならない。
- If あるファイルが `.claude/skills/**` のディレクトリ改名を Bash の `git mv` で行う必要があるとき、Then `workflow-guard.sh` の Bash allowlist は `ai-asset-implementation` type のチケット作業中に限りこれを許可しなければならない。

### ワーク完了チェックポイント

- When ワーク（`work-*`）配下の全タスクが完了したとき、Shall 報告の前に「ワーク完了チェックポイント」（汎用定義では敵対的レビューエージェントによる承認の位置づけ）を仕様上明記しなければならない。ただし自動起動の実装は本要件のスコープ外とする。
- When `work-ticket-driven` がワーク完了チェックポイントを実施するとき、Shall 1つの作業タイプ（`workflow-types.json` の `types`）に属するチケット群を1つのワークとみなし、その完了時点（次のチケットの type が変わる、または todo が空になる時点）でチェックポイントを発火しなければならない。
- When `work-ticket-driven` が `workflow-*` スキルから呼ばれているとき、Shall ワーク完了チェックポイントの承認者は人間（MR レビュー）とし、`work-ticket-driven` はワーク完了報告を返して制御を呼び出し元へ戻さなければならない（レビュー往復の実処理は `workflow-*` 側の責務）。
- When `work-ticket-driven` が単独で呼ばれているとき、Shall ワーク完了チェックポイントの承認者は人間（`AskUserQuestion`）としなければならない。
- When ワーク完了チェックポイントで差し戻しとなったとき、Shall 完了済みチケットを未完了に戻さず、同じ作業タイプの追加チケットで対応しなければならない。

---

## 前提条件

- 既存の `work-ticket-driven`（チケット駆動ワークフロー）のフェーズ別アクセス制御フック（`workflow-guard.sh` 等）が継続して機能すること。
- 既存の `workflow-entry.sh`（ワークフロー振り分け実施済み判定）が定義する振り分けスキルの仕組みと矛盾しないこと。

---

## 制約条件

- **技術的制約**: `.claude/hooks/workflow-types.json` の `types` キー（`investigation` 等の作業タイプ名）は本分類とは別概念であり、混同しないこと。リネームの対象にしない。
- **ビジネス的制約**: 特になし。
- **外部的制約**: 既存のフック・スキルの利用者（過去の会話履歴、ドキュメント内のスキル名言及）との後方互換は問わない（リネームであるため）。

---

## 依存関係

- `.claude/hooks/workflow-entry.sh`（ワークフロー振り分け実施済み判定。`workflow-*` を振り分けスキルとして扱う）
- `.claude/hooks/workflow-guard.sh`（チケット駆動ワークフローのフェーズ制御。`work-*` の実行基盤）
- 仕様の詳細は `.claude/docs/10_spec/スキル体系.md` で定義する

---

## 非機能要件

| 項目 | 説明 |
|------|------|
| 一貫性 | 新規スキルを追加する際、既存の3層のどれに属するかを命名規則だけで判断できること |
| 保守性 | リネームに伴う参照更新はチケット駆動ワークフローで分割実施し、各チケット完了時点でテストが通る状態を保つこと |
