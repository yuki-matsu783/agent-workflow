# フェーズ別ワークスキル 要件定義

## 概要

- **背景**: ワーク層（`work-*`）のスキルは `work-ticket-driven` 1 件だけで、全体計画（プランモード）で全チケットを一括作成し、チケット type の切り替わりでワーク境界（人間レビュー）が入る。フェーズごとの「何を入力に、何を成果物として、何をレビューするか」はスキルとして定義されておらず、毎回の全体計画で LLM が組み立てている。そのため作業のたびに成果物の粒度・DoD・レビュー観点がぶれ、人間が「計画の段階で」口を挟む機会も定まっていない。
- **目的**: 全体計画ワーク 1 件と「調査 / 設計 / 実装・テスト / 設計反映 / AI アセット設計 / AI アセット実装」× 計画 / 実施の 12 件、計 13 件の `work-*` スキルを定義し、**計画 → 人間レビュー → 実施 → 人間レビュー → …** の流れを型にする。各スキルはフェーズの入力・成果物・DoD の型・レビュー観点を担い、チケット運用の仕組み（`wip/` の状態遷移・フック・ワーク境界の判定）は `work-ticket-driven` に残す。
- **スコープ**:
  - 含む: 13 スキルの新設、対応するチケット type の追加（`.claude/hooks/workflow-types.json`）、フックのテスト、要件定義書・仕様書（本書と `.claude/docs/10_spec/フェーズ別ワークスキル.md`）、用語辞書と呼び出し元スキル（`workflow-issue-mr-driven` / `work-ticket-driven` / `workflow-quick-request`）の参照更新
  - 含まない: `retrospective` type と振り返りチケットの変更、スキルごとの要件 / 仕様の 1:1:1 文書化（issue #37）、敵対的レビューエージェントの自動起動、フック本体（`workflow-guard.sh` 等）のロジック変更（type 定義の追加のみで実現する）

---

## ユーザーストーリー

**[As a]** Claude Code にチケット駆動で開発を任せる開発者として、

**[I want]** 作業をフェーズ（調査 / 設計 / 実装・テスト / 設計反映 / AI アセット設計 / AI アセット実装）ごとの計画ワークと実施ワークに分け、計画が固まった時点と実施が終わった時点の両方でレビューしたい。

**[So that]** 実施に入る前に方針を正せて手戻りが減り、フェーズごとの成果物と DoD が毎回同じ型で出てくるため。

## 受け入れ基準（Acceptance Criteria）

### スキルの構成

- When 開発者が `.claude/skills/` を見たとき、Shall `work-overall-plan` と、6 フェーズそれぞれの計画スキル `work-<phase>-plan` / 実施スキル `work-<phase>-exec`（phase = `investigation` / `design` / `implementation` / `design-sync` / `ai-asset-design` / `ai-asset-implementation`）の計 13 件が存在しなければならない。
- When 各スキルの SKILL.md を読んだとき、Shall 目的（位置づけ）・入力（前ワークの成果物）・成果物とテンプレート・チケットの起こし方と DoD の型・レビュー観点・次のワークへの引き継ぎが同じ節構成で書かれていなければならない。
- When スキルがチケットの状態遷移・フックのブロック時の対処・ワーク境界の判定を説明する必要があるとき、Shall 手順を複製せず `work-ticket-driven` を参照しなければならない（DRY）。

### 計画ワークと実施ワークの分離

- When 計画ワークが完了したとき（計画書の作成と実施チケットの起票が済んだとき）、Shall ワーク境界に達したとみなされ、人間レビュー（`workflow-issue-mr-driven` 経由なら PR レビュー、単独なら `AskUserQuestion`）を通るまで実施ワークに着手してはならない。
- When 実施ワークが完了したとき、Shall 同様にワーク境界に達し、人間レビューを通るまで次フェーズの計画ワークに着手してはならない。
- When 計画ワークと実施ワークの境界を判定するとき、Shall 既存の `work-boundary.sh status` の規則（todo 先頭チケットの type が直前の done と異なれば境界）だけで判定できなければならない。すなわち計画ワークと実施ワークは**異なるチケット type** を持たなければならない。

### チケット type の追加

- When `.claude/hooks/workflow-types.json` を読んだとき、Shall 全体計画 1 種・各フェーズの計画 6 種・設計（`design`）・設計反映（`design-sync`）の計 9 種の type が追加されており、既存 5 種（`investigation` / `implementation` / `retrospective` / `ai-asset-design` / `ai-asset-implementation`）は名前も許可範囲も変更されていてはならない。
- When `design` または `design-sync` の doing チケットがある状態で `docs/**` への Edit / Write が試行されたとき、Shall フックは確認なしで許可しなければならない。
- When `design` または `design-sync` の doing チケットがある状態で `.claude/**` への Edit / Write が試行されたとき、Shall フックは WF002 で拒否しなければならない（保護パスは貫通しない）。
- When 全体計画 type の doing チケットがある状態で `wip/00_overall_plan/**` への Edit / Write が試行されたとき、Shall フックは確認なしで許可しなければならない（type の allow は global deny より先に評価される既存の判定順で実現し、フックのコードは変更しない）。
- When 計画 type（各フェーズの計画）の doing チケットがある状態で `wip/20_plans/**` と `wip/10_tickets/**` への書き込みが試行されたとき、Shall フックは確認なしで許可しなければならない（計画書の作成と次のチケットの起票のため）。
- When `implementation` type の許可範囲を確認したとき、Shall not `docs/**` が追加されていてはならない（実装中に設計書を書き換えず、設計反映ワークに寄せる）。
- When 新 type を追加したとき、Shall フックのテスト（`.claude/hooks/tests/*.sh`）に上記の許可 / 拒否のケースが追加され、既存のケースとあわせてすべて通らなければならない。

### ワークの連鎖（チケットを誰が起こすか）

- When `work-overall-plan` が実行されたとき、Shall 依頼に対して使うフェーズ列（不要なフェーズは省略可）を決めて全体計画を `wip/00_overall_plan/` に書き、**最初の計画ワークのチケット 1 枚だけ**を `wip/10_tickets/00_todo/` に起こさなければならない。
- When 計画ワーク `work-<phase>-plan` が実行されたとき、Shall そのフェーズの計画書を `wip/20_plans/` に書き、同フェーズの実施チケット群と、全体計画で決めた次フェーズの計画チケット 1 枚を起こさなければならない（連番は実施順に単調増加させ、挿入や飛び番を要しない）。
- When 実施ワーク `work-<phase>-exec` でレビューが差し戻されたとき、Shall 既存の規則どおり同じ type の追加チケットで対応し、完了済みチケットを doing に戻してはならない。
- When フェーズ列の最後の実施ワークが完了したとき、Shall 既存の `retrospective` チケットに続き、以降は `workflow-issue-mr-driven` の完了処理に戻らなければならない。

### 設計書の置き場と設計反映

- When 設計ワーク（`work-design-exec`）が成果物を作るとき、Shall 一般のソフトウェア設計書（要件定義書・仕様書）を `docs/**` に置き、作成には `task-requirements` / `task-spec` を使わなければならない（`.claude/docs/` は AI アセット用であり使わない）。
- When 設計反映ワーク（`work-design-sync-exec`）が実行されたとき、Shall 実装・テストで判明した差分・決定事項を `docs/**` の設計書に書き戻し、設計と実装が一致していることを DoD で確認しなければならない。
- When AI アセット設計ワーク（`work-ai-asset-design-exec`）が成果物を作るとき、Shall `.claude/docs/`（要件定義書・仕様書・用語辞書）に置き、AI アセット実装ワーク（`work-ai-asset-implementation-exec`）はフック・ルール・スキル・`settings.json` を成果物とし、`task-ai-asset-creator` を使わなければならない。

### 呼び出し元との整合

- When `workflow-issue-mr-driven` が手順 5（ワークループ）に初めて入るとき、Shall `work-overall-plan` から開始し、以降は全体計画のフェーズ列に従って各計画 / 実施スキルを読み込まなければならない。
- When `work-ticket-driven` を単独で（issue / PR の文脈なしに）使うとき、Shall 同様に `work-overall-plan` を入口として使えなければならない。
- When 用語辞書（`.claude/docs/90_glossary/`）を読んだとき、Shall 13 スキルと 9 type が一覧に載っていなければならない。

### アルタナティブフロー（代替経路）

- If 依頼が AI アセット（フック・スキル・ルール・エージェント・設定）の作成・変更である場合、Then 全体計画は「調査 → AI アセット設計 → AI アセット実装 → 振り返り」を標準のフェーズ列としなければならない（`design` / `design-sync` は使わない）。
- If 依頼が一般のソフトウェア変更である場合、Then 全体計画は「調査 → 設計 → 実装・テスト → 設計反映 → 振り返り」を標準のフェーズ列としなければならない。
- If 全体計画で不要と判断したフェーズがある場合（例: 既存設計書が無い小さな修正で設計反映を省く）、Then その理由を全体計画に書いた上で省略してよい。
- If 既存の全体計画（プランモードで作成した `wip/00_overall_plan/*.md`）が既に存在する状態で再開した場合、Then `work-overall-plan` は新しい全体計画を作らず、既存のものを入力として扱わなければならない（冪等性）。

### 例外フロー（エラーケース）

- If 計画ワークが次フェーズの計画チケットを起こし忘れたまま完了した場合、Then 実施ワーク完了後に todo が空になり最後のワークとして扱われてしまうため、計画ワークの DoD に「次フェーズの計画チケットを起票した（最後のフェーズなら振り返りチケット）」を含めなければならない。
- If 全体計画のフェーズ列に無い type のチケットが起こされた場合、Then レビュー観点でその理由を人間に示さなければならない（フックは検知しない。判断は人間に残す）。
- When ヘッドレス実行（`claude -p` 等）でワーク境界に達したとき、Shall 既存の `workflow-issue-mr-driven` の規則どおりレビュー依頼を出した時点でセッションの応答を終え、`AskUserQuestion` で待ってはならない。

## 前提条件

- `work-ticket-driven` とその実行基盤（`workflow-guard.sh` / `workflow-boundary.sh` / `work-boundary.sh` / `merge-prep.sh`）が現行どおり動作すること。
- ワーク境界の判定が「隣接するチケットの type の差」で行われること（`.claude/docs/10_spec/スキル体系.md`「ワーク境界」）。
- 作業タイプの allow / deny / ask が `.claude/hooks/workflow-types.json` の外部定義で追加でき、type の allow が global deny より先に評価されること（`.claude/docs/10_spec/チケット駆動ワークフロー.md`「判定順序」）。

---

## 制約条件

- **技術的制約**: 既存 5 type の名前・許可範囲は変更しない。`retrospective` type と振り返りチケットは変更しない。フック本体のロジックは変更せず、type 定義の追加とテストの追加だけで実現する。スキル名は `work-` prefix の英小文字・ハイフンとし、3 層構造（`.claude/docs/10_spec/スキル体系.md`）の `work-*` に分類する。
- **ビジネス的制約**: スキルごとの要件定義書・仕様書の 1:1:1 対応は issue #37 で整理する。本要件では 13 スキルをまとめて本書と仕様書 1 組で扱う。
- **外部的制約**: `.claude/rules/markdown-frontmatter.md`（SKILL.md には `title` / `type: skill` / `tags` / `keywords` を追加し `description` は Claude Code 用の実キーとして流用する）、`.claude/rules/claude-config-headless-awareness.md`（人間の確認を待つ手順にはヘッドレス実行時の挙動を併記する）に従う。

- `.claude/skills/workflow-issue-mr-driven/`（ワークループの呼び出し元）
- `.claude/skills/task-requirements/`、`task-spec/`、`task-ai-asset-creator/`（実施ワークが成果物の作成に使うタスクスキル）
- 仕様の詳細は `.claude/docs/10_spec/フェーズ別ワークスキル.md` で定義する

## 非機能要件

| 項目 | 説明 |
|------|------|
| 一貫性 | 13 スキルの SKILL.md は同じ節構成・同じ frontmatter キーを持ち、どのフェーズでも同じ読み方ができること |
| 保守性 | フェーズの追加・変更が「type 定義の追加 + スキル 2 件の追加」で済むこと。チケット運用の手順は `work-ticket-driven` 1 箇所に集約すること |
| テスト容易性 | 新 type の許可範囲は既存のフックテスト（stdin JSON → exit code）の形式で検証できること |
| ヘッドレス適合 | 人間レビュー待ちの扱いは既存の `workflow-issue-mr-driven` の規則（`request` で応答を終える）を踏襲し、新たな `ask` を追加しないこと |
