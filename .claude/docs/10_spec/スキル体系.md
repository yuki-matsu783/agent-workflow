# スキル体系 仕様書

## 概要

- **背景・目的**: `.claude/docs/00_requirements/スキル体系.md` を参照。
- **スコープ**:
  - 含む: 3層（workflow/work/task）の定義・命名規則・承認方式、既存スキルのリネーム対応表、`work-ticket-driven` における用語対応、ワーク完了チェックポイントの位置と入出力、`work-ticket-driven` におけるワークの単位（ワーク境界）と現行の承認者（人間）、`workflow-guard.sh` の `git mv` 許可拡張の仕様
  - 含まない: 敵対的レビューエージェントの自動起動ロジックの実装仕様（汎用定義上の将来の承認者として残すが、実装は対象外）

---

## 3層の定義

| 層 | 命名 prefix | 実現単位 | チェックポイント | 承認者 |
|---|---|---|---|---|
| ワークフロー | `workflow-*` | ワーク（`work-*`）の組み合わせ | ワーク間に必ず設置 | 人間（MRレビュー または `AskUserQuestion`） |
| ワーク | `work-*` | タスク（`task-*` 相当の実行単位、チケット駆動ワークフローではチケット）の組み合わせ | 複数タスク完了時点に設置 | 汎用定義は敵対的レビューエージェント（本仕様では位置と入出力のみ定義。自動起動の実装は対象外）。**`work-ticket-driven` の現行運用は人間**（下記「ワーク完了チェックポイント」） |
| タスク | `task-*` | 作業レベルの手順 | チェックポイントなし | 実行者自身によるセルフレビュー |

判定基準（要件定義書のAcceptance Criteriaと同一）:

1. ワーク間に人間承認が必須のスキル → `workflow-*`
2. タスク相当の組み合わせで、ワーク内は人間承認不要、完了時に敵対的レビューが入るスキル → `work-*`
3. セルフレビューで完結する作業レベルのスキル → `task-*`

[`.claude/hooks/workflow-types.json`](../90_glossary/チケットtype.md#investigation) の `types`（`investigation` / `implementation` / `retrospective` / `ai-asset-design` / `ai-asset-implementation`）は**チケットの作業タイプ名**であり、本仕様の「タスク」とは別の識別子体系。[`work-ticket-driven`](../90_glossary/スキル名.md#work-ticket-driven) におけるチケットは3層構造の「タスク」に相当するが、フック実装との整合を優先し、JSON のキー名・チケットの呼称（「チケット」）は変更しない。

## ワーク完了チェックポイント

`work-*` スキルは、1つのワークに属する全タスクが完了した時点で、報告の前に以下のチェックポイントを設置する。

| 項目 | 内容 |
|------|------|
| 位置 | 1つのワークの完了直後、次のワークの着手前 |
| レビュー対象 | ワーク開始コミット（そのワークの最初のタスク着手時のコミット）から現在までの全差分 |
| 出力 | 承認 / 差し戻し（差し戻し時は**同じワークへの追加タスク**で対応する。完了済みタスクを未完了に戻さない） |
| 承認者（汎用定義） | 敵対的レビューエージェント（自動起動の実装は本仕様のスコープ外。将来の `work-*` スキルが実装する余地として残す） |
| 承認者（`work-ticket-driven` の現行運用） | **人間**。`workflow-*` 経由で呼ばれた場合は MR（PR）レビュー、単独で呼ばれた場合は `AskUserQuestion` による確認 |

### `work-ticket-driven` におけるワークの単位（ワーク境界）

`work-ticket-driven` では、**1つの作業タイプ（`.claude/hooks/workflow-types.json` の `types` キー。`investigation` / `implementation` / `retrospective` / `ai-asset-design` / `ai-asset-implementation`）に属するチケット群を1つのワーク**とする。チケットを done に移した時点で、todo の先頭チケットの `type` が異なる、または todo が空であれば**ワーク境界**に達したとみなし、上記チェックポイントを発火する。

| 呼び出し元 | チェックポイントの実現方法 |
|------|------|
| `workflow-issue-mr-driven`（`workflow-*`） | `work-ticket-driven` はワーク完了報告を返して**制御を呼び出し元へ戻す**。push・PR 本文更新・レビュー依頼・レビューコメントの取得・差し戻し（追加チケット）の判断はすべて `workflow-issue-mr-driven` 側の責務。この場合、ワーク層の本チェックポイントとワークフロー層の「ワーク間の人間承認」は**同一の発火点・同一のレビュー行為**であり、二重にレビューを要求しない |
| 単独（issue / PR の文脈なし） | `work-ticket-driven` 自身が `AskUserQuestion` で「承認 / 差し戻し」を確認する。ヘッドレス実行では応答が得られず拒否として扱われるため、単独実行を非対話環境で行うことは想定しない |

レビュー往復の実処理（ターンの終了と再開、追加チケットの作成手順）は `.claude/docs/10_spec/issue-PR駆動ワークフロー.md` と各スキルの SKILL.md が正である。**ワーク境界の判定とレビュー状態の遷移は LLM の判断に委ねず、`.claude/hooks/work-boundary.sh`（`status` / `request` / `complete`）が決定論的に行う。** レビュー状態は `wip/10_tickets/review-state.json` に置き、このスクリプト以外からの書き換え（Edit / Write / Bash）はフック `workflow-boundary.sh` が WF012 で拒否する。レビューが完了していないのに次のワークへ着手する操作は同フックが WF011 で拒否し、理由と対処を stderr で返す。`request` / `complete` は GitHub の実操作（コメント投稿・取得）を自ら行って証跡を記録するため、LLM が「依頼した」「確認した」と主張するだけでは状態は進まない。仕様の正は `.claude/docs/10_spec/チケット駆動ワークフロー.md`「ワーク境界の判定とレビュー状態」。`workflow-guard.sh` 自体は変更せず、doing が空である間は従来どおり GitHub 操作を許可する。

ワークフロー層の完了処理（全ワーク完了後の draft 解除）も同じ方針で機械化する。`workflow-issue-mr-driven` はマージ前作業（wip の成果物のリセット → default ブランチとのコンフリクト確認 → 関連 issue へのコメント）を `.claude/hooks/merge-prep.sh`（`reset-wip` / `check-conflicts` / `notify-issue` / `ready`）に委ね、証跡は `wip/merge-prep.json` に残る。`ready` は先行ステップの記録と再検証を通ったときだけ `gh pr ready` を実行し、直接の `gh pr ready` は `workflow-boundary.sh` が WF015 で拒否する（前提未充足は WF016）。仕様の正は `.claude/docs/10_spec/チケット駆動ワークフロー.md`「マージ前作業の判定と状態」と `.claude/docs/10_spec/issue-PR駆動ワークフロー.md`「完了処理」。マージ自体は人間が行う。

`work-ticket-driven` の場合、既存の `retrospective` チケット（セルフレビュー・結果報告の作成、タスク層の役割）は本チェックポイントと**別物**として維持する。retrospective は「実行者自身の振り返り」、ワーク完了チェックポイントは「第三者（人間、汎用定義では敵対的レビューエージェント）による承認」であり、両者を統合しない。なお retrospective 自体も1つのワークであるため、その完了時にも他の作業タイプと同様にチェックポイントが発生する。結果報告（`wip/30_reports/`）の「レビュー結果」欄には、各ワークのチェックポイントの結果（承認 / 差し戻し回数）を記録する。

## `workflow-guard.sh` の `git mv` 許可拡張

### 背景

`.claude/hooks/workflow-guard.sh` の `wf_validate_mv()` は、`mv` / `git mv` の対象パスを `wip/10_tickets/**` 配下のみに限定している。スキルのリネーム作業（`.claude/skills/**` の `git mv`）はこの制約でブロックされる（WF003）。

### 仕様

`ai-asset-implementation` type の doing チケットが存在する間に限り、`.claude/skills/**` 配下の `mv` / `git mv` を許可する。

```bash
wf_validate_mv() {
    local tok
    for tok in "$@"; do
        case "${tok}" in
            -*) continue ;;
            QUOTED) return 1 ;;
        esac
        case "${tok//\\//}" in
            wip/10_tickets/*) continue ;;
            .claude/skills/*)
                [ "${TICKET_TYPE}" = "ai-asset-implementation" ] && continue
                return 1
                ;;
            *) return 1 ;;
        esac
    done
    return 0
}
```

- `TICKET_TYPE` は既存のグローバル変数（doing チケットの frontmatter `type` から `workflow-lib.sh` の `wf_init` がセットする）をそのまま使う。追加の状態管理は不要。
- Edit/Write ツールでの `.claude/skills/**` への書き込み許可は、`ai-asset-implementation` type の `allow_paths` に既に含まれているため変更不要（パス判定 `wf_resolve` は Bash の `git mv` 判定とは独立した経路）。
- この拡張により、`ai-asset-implementation` 以外の type（investigation・implementation・retrospective・ai-asset-design）では従来どおり `.claude/skills/**` の `git mv` はブロックされる。
