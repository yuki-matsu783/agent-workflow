# フェーズ別ワークスキル 仕様書

## 概要

- **背景**: 要件定義書 `.claude/docs/00_requirements/フェーズ別ワークスキル.md` に基づき、13 スキル・9 type・呼び出し元の変更を実装可能なレベルで確定する。
- **目的**: 「どのスキルがどの type を使い、どのパスに何を書き、誰が次のチケットを起こし、人間は何をレビューするか」を一意に決め、13 スキルの SKILL.md が同じ型で書ける状態にする。
- **スコープ**:
  - 含む: スキル × type 対応表、各 type の許可範囲、ワークの連鎖規則（チケットの起票責任・連番・最後のフェーズ）、type からスキルを選ぶ規則、SKILL.md の節構成と frontmatter、テンプレート方針、`EnterPlanMode` の扱い、呼び出し元スキルへの変更点、テストシナリオ
  - 含まない: 各 SKILL.md の文言、フック本体の変更（type 定義の追加のみ）、`retrospective` の変更、敵対的レビューエージェント

## 入力（Input）定義

### 入力元

- **入力元**: `workflow-issue-mr-driven`（ワークループ）または単独実行のユーザー。前ワークの成果物（`wip/00_overall_plan/`、`wip/20_plans/`、`docs/**`、`.claude/docs/**`、コード差分）と issue の受け入れ条件。

### 入力データ（各ワークが受け取るもの）

| 項目名 | 型 | 必須 | 説明 | デフォルト値 |
|--------|----|------|------|-------------|
| 全体計画 | file | Y（全体計画ワーク以外） | `wip/00_overall_plan/*.md`。フェーズ列・各フェーズの狙い・対象 issue / PR | |
| 前フェーズの計画書 / 成果物 | file | N | 計画ワークは前フェーズの実施成果物、実施ワークは同フェーズの計画書 | |
| issue の受け入れ条件 | text | N | `workflow-issue-mr-driven` 経由のとき。DoD とレビュー観点に落とす | |
| `todo_head_type` | string | Y | `bash .claude/hooks/work-boundary.sh status` の出力。次に読み込むスキルを決める（後述） | |

### 入力フォーマット（`work-boundary.sh status` の抜粋）

```json
{
  "last_done_type": "investigation-plan",
  "todo_head": "003-investigation-現状調査.md",
  "todo_head_type": "investigation",
  "at_boundary": true,
  "review_state": "completed"
}
```

- **出力先**: `wip/00_overall_plan/`（全体計画）、`wip/20_plans/`（計画書・調査結果）、`wip/10_tickets/00_todo/`（次のチケット）、`docs/**`（設計書）、`src/**` 等（実装）、`.claude/docs/**`（AI アセット設計）、`.claude/hooks|rules|skills/**`・`.claude/settings.json`（AI アセット実装）。

- 既存 5 type の名前・`allow_paths`・`bash_groups` は変更しない。`implementation` に `docs/**` を足さない（設計書の更新は設計反映ワークに寄せる）
- 計画 type はすべて同じ許可範囲（`wip/20_plans/**`）だが、**フェーズごとに別 type** にする。理由: (1) `work-boundary.sh status` の `todo_head_type` からスキルが一意に決まる（共通 `plan` だとチケット名の slug を読む必要がある）、(2) レビュー依頼・チケット名・結果報告の「レビュー結果」欄にフェーズが出る、(3) コストは JSON のエントリ 6 件だけ
- `overall-plan` は global deny（`wip/00_overall_plan/**`）を type の allow で貫通する。判定順（`チケット駆動ワークフロー.md`「判定順序」）で `types.<type>.allow_paths` が `global.deny_paths` より先に評価されるため、フックのコード変更は不要
- チケットの起票（`wip/10_tickets/00_todo/` への Write）は `global.allow_paths` で常に許可される。計画ワークはこれを使って次のチケットを起こす

### type からスキルを選ぶ規則

呼び出し元（`workflow-issue-mr-driven` / 単独の `work-ticket-driven`）は、`work-boundary.sh status` の `todo_head_type` から次に読み込むスキルを機械的に決める。

| `todo_head_type` | 読み込むスキル |
|---|---|
| `overall-plan` | `work-overall-plan` |
| `<phase>-plan` | `work-<phase>-plan` |
| `<phase>`（`investigation` / `design` / `implementation` / `design-sync` / `ai-asset-design` / `ai-asset-implementation`） | `work-<phase>-exec` |
| `retrospective` | `work-ticket-driven`（手順 4 の retrospective） |
| null（todo が空） | ワークループ終了 → `workflow-issue-mr-driven` の完了処理 |

### ステータスコード

スキル固有のエラーコードは追加しない。フックの WF001〜WF016 は `チケット駆動ワークフロー.md` のとおり。

## 処理フロー

### 基本フロー（ハッピーパス: ソフトウェア変更）

1. `work-overall-plan`: `001-overall-plan-全体計画.md` を todo に起こして着手する。依頼と issue の受け入れ条件から**フェーズ列**を決め、全体計画を `wip/00_overall_plan/<slug>.md` に Write する。最初の計画チケット `002-investigation-plan-調査計画.md` を起こして done にする → **ワーク境界（レビュー: 全体計画）**
2. `work-investigation-plan`: 調査計画書を `wip/20_plans/調査計画-<slug>.md` に作り、調査チケット（`003-investigation-…` 〜）と次の計画チケット（`00N-design-plan-設計計画.md`）を起こす → **境界（レビュー: 調査計画）**
3. `work-investigation-exec`: 調査チケットを順に実施し、調査結果を `wip/20_plans/調査結果-<slug>.md` に書く → **境界（レビュー: 調査結果）**
4. `work-design-plan` → 境界 → `work-design-exec`（`docs/**` に要件定義書・仕様書）→ 境界
5. `work-implementation-plan` → 境界 → `work-implementation-exec`（コード・テスト）→ 境界
6. `work-design-sync-plan` → 境界 → `work-design-sync-exec`（`docs/**` を実装に合わせて更新）→ 境界。設計反映の計画ワークは最後のフェーズなので、次の計画チケットの代わりに**振り返りチケット**（`0NN-retrospective-振り返り.md`）を起こす
7. `retrospective`（`work-ticket-driven` 手順 4）→ 境界 → todo が空 → `workflow-issue-mr-driven` の完了処理

AI アセットの場合は 4〜6 が `work-ai-asset-design-plan/exec` → `work-ai-asset-implementation-plan/exec` になり、AI アセット実装の計画ワークが振り返りチケットを起こす。

### ワークの連鎖規則

| 誰が | 何を起こすか | 備考 |
|---|---|---|
| `work-overall-plan` | 自分のチケット（`001-overall-plan-…`）と、フェーズ列の**最初の計画チケット 1 枚** | 全チケットを一括作成しない |
| `work-<phase>-plan` | 同フェーズの実施チケット群（1 枚以上）と、フェーズ列の**次の計画チケット 1 枚**。次が無ければ**振り返りチケット 1 枚** | DoD に「次の計画チケット（または振り返りチケット）を起票した」を必ず含める。起こし忘れると実施ワーク完了後に todo が空になり、最後のワークとして完了処理に入ってしまう |
| `work-<phase>-exec` | 起こさない。レビューの差し戻しは**呼び出し元**が同 type の追加チケットを起こす（既存規則） | |

- 連番 `NNN` は実施順に単調増加させる。連鎖方式では「次に起こすチケット」は常に todo の末尾より後になるため、飛び番や挿入は生じない（差し戻しの追加チケットで飛ぶのは既存どおり）
- `depends_on` は同フェーズ内では直前のチケット、計画チケットは前フェーズの最後の実施チケット
- 全体計画で「省略する」と決めたフェーズは起こさない。フェーズ列に無い type のチケットを起こす必要が生じたら、計画書にその理由を書き、レビュー観点で人間に示す（フックは検知しない）

### 代替フロー

1. **既存の全体計画がある**（プランモードで作った `wip/00_overall_plan/*.md` が存在する、または再開）: `work-overall-plan` は新しい全体計画を作らず、既存のものを読んでフェーズ列を確認し、最初の計画チケットが未起票なら起こすだけにする（冪等）
2. **フェーズを省略する**: 全体計画に理由を書けば省略できる。省略したフェーズの計画チケットは起こさず、直前の計画ワークが「次の計画チケット」としてその次のフェーズを起こす
3. **単独実行**（issue / PR なし）: `work-ticket-driven` 手順 1 の入口として `work-overall-plan` を使う。ワーク境界の承認は `AskUserQuestion`（既存規則）
4. **差し戻し**: 呼び出し元が同 type の追加チケットを起こす。計画ワークの差し戻しなら計画 type の追加チケット（計画書の修正・実施チケットの見直し）、実施ワークならその type の追加チケット

### 例外フロー

1. 計画ワークが次の計画チケットを起こさずに done にしようとした → DoD 未充足として done にしない（スキルの手順で確認する。フックは検知しない）
2. `todo_head_type` に対応するスキルが無い（未知の type）→ フックが WF004 で止める前に、呼び出し元は type 定義（`workflow-types.json`）とスキル一覧の不整合として報告して停止する
3. ヘッドレス実行でワーク境界に達した → 既存規則どおり `request` を出して応答を終える。本仕様で新たな `ask` は追加しない

## データ設計

### 全体計画の書式（`wip/00_overall_plan/<slug>.md`）

frontmatter は `type: plan`（`markdown-frontmatter.md`）。本文の必須項目:

```markdown
# 全体計画: <依頼の要約>

- 対象 issue: #N <url>（無ければ「なし」）
- PR: #M <url>（同上）
- ブランチ: <branch>

## Context
<背景・目的・合意事項>

## フェーズ列
| 順 | フェーズ | 計画スキル / 実施スキル | 狙い | 省略理由（省略時） |

## 受け入れ条件との対応
<issue の受け入れ条件 → どのフェーズの成果物で満たすか>

## 判断が必要になりそうな点
```

### 計画書の書式（`wip/20_plans/`）

`work-ticket-driven/assets/plan.template.md`（`type: plan`）を共通の土台にする。計画ワークは「実装ステップ」節を**実施チケットの一覧（ファイル名・目的・DoD）**として使い、「変更対象ファイル」節の `allowed_paths 案` を実施チケットの frontmatter に転記する。調査結果（`work-investigation-exec`）は同テンプレートの「調査サマリ」「リスク・未解決事項」を主に使う。

### テンプレート方針

| スキル | テンプレート |
|---|---|
| `work-overall-plan` | 自前 `assets/overall-plan.template.md`（上記書式。プランモードの出力と互換な `type: plan`） |
| 計画スキル 6 件 | `work-ticket-driven/assets/plan.template.md` を Read → Write。フェーズ固有の節が要る場合だけ自前の `assets/<phase>-plan.template.md` を置く（既定は置かない） |
| `work-investigation-exec` | `plan.template.md`（調査結果として使う） |
| `work-design-exec` / `work-ai-asset-design-exec` | `task-requirements` / `task-spec` のテンプレート |
| `work-implementation-exec` | なし（コード） |
| `work-design-sync-exec` | なし（既存設計書を Edit。レビュー記録にバージョンを追記） |
| `work-ai-asset-implementation-exec` | `task-ai-asset-creator` のテンプレート |

### SKILL.md の節構成（13 スキル共通）

frontmatter: `name`、`description`（Claude Code 用。トリガー語を含む）、`title`、`type: skill`、`tags`、`keywords`（`.claude/rules/markdown-frontmatter.md`）。

| # | 節 | 内容 |
|---|---|---|
| 1 | 位置づけ | 前後のワーク、対応する type、`work-ticket-driven` への委譲（チケットの状態遷移・フックのブロック時の対処・境界判定は再掲しない） |
| 2 | 入力 | 前ワークの成果物（パス）、issue の受け入れ条件、全体計画のフェーズ列 |
| 3 | 成果物とテンプレート | 出力先パスと使うテンプレート（上表） |
| 4 | チケットの起こし方と DoD の型 | 計画: 実施チケット群 + 次の計画チケットの起こし方、DoD の定型項目。実施: チケットごとの DoD の型 |
| 5 | レビュー観点 | ワーク境界で人間に見てもらう点。`work-boundary.sh request --body-file` の本文の元にする |
| 6 | 次のワークへの引き継ぎ | 次に読み込まれるスキルと、渡す成果物 |
| 7 | エラーハンドリング | このスキル固有のもののみ。フックの WF コードは `work-ticket-driven` を参照 |

### レビュー観点の型

| ワーク | 観点 |
|---|---|
| 全体計画 | フェーズ列が依頼と受け入れ条件に対して過不足ないか、省略理由が妥当か、判断点が洗い出されているか |
| 計画 | 実施チケットの粒度（1 チケット = 1 成果物）、DoD が検証可能か、`allowed_paths` 案が最小か、次の計画チケット（または振り返り）が起票されているか、計画書が前フェーズの成果物と整合するか |
| 実施 | DoD がすべて満たされているか、差分が計画の範囲内か、テスト結果、計画からの逸脱とその理由 |

## インターフェース定義

### 呼び出し元スキルへの変更点

| スキル | 変更 |
|---|---|
| `workflow-issue-mr-driven` | 手順 5 の初回入口を「`work-ticket-driven` 手順 1」から「`work-overall-plan`」に変更。各ループで `todo_head_type` → スキルの対応表に従って計画 / 実施スキルを読み込む。役割分担表・フロー図に 13 スキルを追記。差し戻し時の追加チケット作成は現行どおり `work-ticket-driven` の手順 2 の要領 |
| `work-ticket-driven` | 手順 1（全体計画）を `work-overall-plan` に委ねる形に改訂（プランモードは代替経路として残す）。手順 2（チケット作成）を「計画ワークが連鎖的に起こす」前提に改訂し、一括作成は単独実行の代替経路として残す。手順 4 の type 別の説明に 9 type を追加。`references/permission-matrix.md`・`assets/ticket.template.md` の type 一覧を更新 |
| `workflow-quick-request` | 振り返りからの切り替え時のチケット構成の記述を「`work-overall-plan` が AI アセットのフェーズ列で起こす」に合わせる |

### `EnterPlanMode` の扱い

- `work-overall-plan` の導入後も `EnterPlanMode` は禁止しない。doing が空のときだけ使える現行の規則（WF006）と `plansDirectory`（`wip/00_overall_plan`）はそのまま
- 標準の入口は `work-overall-plan`（チケットとして記録が残り、境界で PR レビューを受けられる）。プランモードで作った全体計画がある場合は代替フロー 1 のとおり入力として扱う
- WF006 のメッセージ文言は変更しない（「計画の見直しは investigation チケットで」は、計画 type のチケットでも成立する）

```json
}
```

`design-plan` / `implementation-plan` / `design-sync-plan` / `ai-asset-design-plan` / `ai-asset-implementation-plan` は `investigation-plan` と同じ形（`allow_paths: ["wip/20_plans/**"]`）で、description だけフェーズに合わせる。

---

## エラーハンドリング

スキル固有のエラーコードは設けない。想定される失敗と対処:

| 状況 | 対処 |
|------|------|
| 計画ワークで次の計画チケットを起こし忘れた | DoD 未充足。done にせず起票する。done にしてしまった後に気付いたら、呼び出し元が同 type の追加チケットではなく**次の計画チケットを直接 todo に起こす**（計画チケットの起票は `global.allow_paths` で誰でもできる） |
| `todo_head_type` がスキル対応表に無い | type 定義とスキルの不整合。報告して停止する |
| 計画 type のチケットで `src/**` 等に書こうとした | WF009（未記載パスの確認）。計画ワークでコードは触らない。実施チケットに回す |
| `design` で `.claude/**` に書こうとした | WF002。AI アセットは `ai-asset-design` / `ai-asset-implementation` のフェーズで扱う |

## 前提条件

- `work-ticket-driven` の実行基盤（`workflow-guard.sh` / `workflow-boundary.sh` / `work-boundary.sh` / `merge-prep.sh`）が現行どおり動作すること
- ワーク境界が隣接チケットの type の差で判定されること
- `types.<type>.allow_paths` が `global.deny_paths` より先に評価されること

---

## 制約条件

- **技術的制約**: 既存 5 type と `retrospective` は変更しない。フック本体は変更せず、type 定義とテストの追加のみ。スキル名は `work-` prefix の英小文字・ハイフン
- **ビジネス的制約**: スキルごとの要件 / 仕様の 1:1:1 対応は issue #37 で整理する
- **外部的制約**: `.claude/rules/markdown-frontmatter.md`、`.claude/rules/claude-config-headless-awareness.md`

---

## 非機能要件

| 項目 | 説明 |
|------|------|
| 一貫性 | 13 スキルは同じ節構成・同じ frontmatter キー |
| 保守性 | フェーズの追加は「type 2 件 + スキル 2 件 + 本仕様の対応表 1 行」で済む |
| テスト容易性 | 新 type の許可範囲は既存のフックテスト形式（stdin JSON → exit code）で検証する |
| ヘッドレス適合 | 新たな `ask` を追加しない。境界待ちは既存の `request` で応答を終える規則に従う |
