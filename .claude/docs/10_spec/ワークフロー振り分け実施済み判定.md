# ワークフロー振り分け実施済み判定 仕様書

> 本文書は特定の1スキルに1:1で紐づく要件/仕様ではなく、複数スキルが参照する横断的なメタ文書である。

## 概要

- **背景**: CLAUDE.md「作業の振り分け」で、ユーザーからのすべての依頼は `workflow-issue-mr-driven`（開発作業）か `workflow-quick-request`（軽作業）のどちらかを読み込んでから着手すると定めた。指示だけでは Claude が読み飛ばしても検知できないため、**どちらかのスキルが読み込まれたことを機械的に確認し、未読なら作業をブロックする**フックを設ける。
- **目的**: プロンプトごとに「振り分けスキルの宣言 → 作業」の順序を強制し、宣言の有無をログと状態ファイルで追跡できるようにする。
- **スコープ**:
  - 含む: フック `.claude/hooks/workflow-entry.sh` の入出力、状態ファイル、エラーコード、テストシナリオ
  - 含まない: 振り分けスキルの中身（各 SKILL.md）、チケット駆動ワークフローのフック（`workflow-guard.sh` / `workflow-diff-check.sh`。仕様は `チケット駆動ワークフロー.md`）

## 入力（Input）定義

### 入力元

Claude Code のフック機構。3 つのイベントで同じスクリプトを第 1 引数（モード）を変えて呼ぶ。

| モード | イベント | matcher | 役割 |
|--------|---------|---------|------|
| `prompt` | UserPromptSubmit | （なし） | プロンプト連番を進め、宣言をリセットする。`/<振り分けスキル名>` で始まるプロンプトは宣言扱い |
| `record` | PostToolUse | `Skill` | 振り分けスキルの読み込みを宣言として記録する |
| `guard` | PreToolUse | `Edit\|Write\|NotebookEdit\|Bash\|EnterPlanMode\|Agent\|Workflow` | 未宣言なら exit 2（WF101） |

### 入力データ（stdin JSON）

| 項目名 | 型 | 使うモード | 説明 |
|--------|----|-----------|------|
| `session_id` | string | 全部 | 状態ファイルのキー。`A-Za-z0-9_-` 以外は除去。空なら `unknown` |
| `prompt` | string | prompt | ユーザーのプロンプト。1 行目が `/<振り分けスキル名>`（単語境界まで完全一致）ならスラッシュ起動 |
| `tool_name` | string | record / guard | `record` は `Skill` のときだけ処理する |
| `tool_input.skill` | string | record | 読み込まれたスキル名。振り分けスキル（下記）と完全一致したときだけ記録する |
| （ファイルシステム）`wip/10_tickets/00_todo/*.md`、`10_doing/*.md` | — | prompt / guard | チケット駆動ワークフローの進行状態。1 つでもあれば継続中とみなす（下記「継続条件」） |
| （ファイルシステム）`wip/10_tickets/20_done/*.md`、`wip/10_tickets/review-state.json` | — | prompt / guard | 最後のワークのレビュー待ち判定に使う。`review-state.json` の `state` が `requested` かつ `ticket` が `20_done` の最終チケット（ファイル名先頭の連番が最大のもの）と一致すれば継続中とみなす（下記「継続条件」） |

### 振り分けスキル（定数 `WF_ENTRY_SKILLS`）

`workflow-issue-mr-driven`、`workflow-quick-request`。追加する場合はスクリプトの定数と CLAUDE.md「作業の振り分け」を合わせて更新する。`work-ticket-driven` や `task-gh-issue` など、振り分けから委譲されるスキルの読み込みは宣言にならない。

### 状態ファイル（`.claude/hooks/.state/<session_id>.entry`）

Git 管理外（`.gitignore` 済み）。`key=value` 形式で 3 行。

| キー | 説明 |
|------|------|
| `prompt_seq` | プロンプト連番。UserPromptSubmit のたびに +1 |
| `workflow` | 最後に宣言された振り分けスキル名 |
| `declared_seq` | 宣言時の `prompt_seq` |

**宣言済み** = `workflow` が空でなく、かつ `declared_seq == prompt_seq`。つまり宣言はプロンプトごとに必要で、前のプロンプトの宣言は引き継がれない。ファイルが無い・壊れている場合は `prompt_seq=0` / 未宣言として扱う（フック導入直後でも Skill の読み込みで復旧できる）。

### 継続条件（チケットの有無による自動継続）

`wip/10_tickets/00_todo/` または `wip/10_tickets/10_doing/` に `*.md` が 1 つでもあれば、**`workflow-issue-mr-driven` の作業が進行中**とみなし、宣言の有無にかかわらず `guard` を許可する（状態ファイルは更新しない。判定は呼び出しのたびにディレクトリを見る）。

`00_todo` / `10_doing` が両方空でも、`wip/10_tickets/review-state.json` が `requested`（かつ `ticket` が `20_done` の最終チケットと一致）なら、**最後のワークのレビュー待ち**とみなして同様に継続を許可する。全チケット done 後に `work-boundary.sh request` → 人間レビュー → `complete` → PR の ready 化（`workflow-issue-mr-driven` 手順 6）を行う間は todo / doing が空になるため、この判定が無いと次のプロンプトで宣言を要求されてしまう（#28）。判定規則は `work-boundary.sh` の `wb_compute`（`REVIEW_STATE` は `review-state.json` の `ticket` が `20_done` の最終チケット= ファイル名先頭の連番が最大のものと一致するときだけ有効）と揃えている。`ticket` が最後の done と不一致（別のワークの古い状態が失効せず残っている）なら継続とみなさない。

| 状態 | 判定 |
|------|------|
| `00_todo` または `10_doing` にチケットあり | 継続中。宣言不要 |
| `20_done` にだけチケットあり、`review-state.json` が `requested`（`ticket` が最終 done と一致） | 継続中（レビュー待ち）。宣言不要 |
| `20_done` にだけチケットあり、`review-state.json` が `completed` / 無い / `ticket` が不一致（失効） | 継続ではない。通常どおり宣言が必要 |
| `wip/10_tickets/` が無い | 通常どおり宣言が必要 |

根拠: チケットがある間は `workflow-guard.sh` が doing チケットの type に基づいて書き込み先とコマンドを統制しているため、振り分けの再宣言を省いても保証は落ちない。レビュー待ちの間も、レビュー状態ファイルの書き換えは `work-boundary.sh`（WF012 で保護）に限定されているため、同様に保証は落ちない。`workflow-quick-request` には継続の証拠となる状態が無いため、こちらは常にプロンプトごとの宣言を求める。

## 出力（Output）定義

| モード | exit | stdout | stderr |
|--------|------|--------|--------|
| prompt | 0 | `hookSpecificOutput.additionalContext` に `[WF-ENTRY]` の案内（宣言を促す / スラッシュ起動を記録した） | — |
| record | 0 | — | — |
| guard（宣言済み） | 0 | — | — |
| guard（未宣言） | 2 | — | `[WF101]` + 対象ツール + 前回の宣言 + 対処 |
| 不明なモード | 0 | — | 設定ミスの案内（作業は止めない） |

### 出力例（UserPromptSubmit）

```json
{
  "hookSpecificOutput": {
    "hookEventName": "UserPromptSubmit",
    "additionalContext": "[WF-ENTRY] プロンプト #3: 作業に着手する前に、Skill ツールで workflow-issue-mr-driven / workflow-quick-request のいずれかを読み込んで振り分けを宣言すること（前回の宣言: workflow-quick-request @#2）。..."
  }
}
```

### 出力例（PreToolUse のブロック）

```
[WF101] ワークフロー未宣言: このプロンプト（#3）では、作業の振り分けとなるスキルがまだ読み込まれていません
対象ツール: Edit
前回の宣言: workflow-quick-request（プロンプト #2）。宣言はプロンプトごとに必要で、前回の宣言は引き継がれません
対処: 作業を始める前に Skill ツールで次のいずれかを呼び、その手順に従ってください: workflow-issue-mr-driven（...）/ workflow-quick-request（...）。ブロックを迂回しないでください。
```

### エラーコード

| コード | 名称 | 発生条件 |
|--------|------|---------|
| WF101 | ワークフロー未宣言 | 現在のプロンプトで振り分けスキルが読み込まれていない状態で、書き込み系・実行系ツール（guard の matcher）が呼ばれた |
| WF-ENTRY | （案内） | ブロックではない。UserPromptSubmit で宣言を促す文脈 |

チケット駆動ワークフローのコード（WF001〜WF010、WF-DIFF）とは番号帯を分ける（1xx = 振り分け）。

## 処理フロー

```
UserPromptSubmit ─→ prompt_seq++ ─┬─ 00_todo / 10_doing にチケットあり → 「継続中・宣言不要」を additionalContext
                                  ├─ レビュー待ち（review-state.json が requested、ticket が最終 done と一致） → 「レビュー待ち・宣言不要」を additionalContext
                                  ├─ 1 行目が /<振り分けスキル> → workflow, declared_seq を更新 → 「記録した」を additionalContext
                                  └─ それ以外 → 「宣言せよ」を additionalContext
Skill(振り分けスキル) の PostToolUse ─→ workflow = skill, declared_seq = prompt_seq
Edit/Write/Bash/... の PreToolUse ─┬─ declared_seq == prompt_seq → 許可（exit 0）
                                  ├─ 00_todo / 10_doing にチケットあり → 許可（exit 0。ログに CONTINUE(ticket)）
                                  ├─ レビュー待ち → 許可（exit 0。ログに CONTINUE(review)）
                                  └─ それ以外 → WF101（exit 2）
```

- `guard` は Read / Glob / Grep / AskUserQuestion / Skill を対象にしない。宣言前の調査や、どちらの振り分けにするかの確認はできる
- ブロック後、Claude が Skill で振り分けスキルを読み込めば `record` が記録し、次の呼び出しから通る
- 両方のフックが同じツールに掛かる場合（例: doing チケットがある状態の Edit）、振り分け実施済み判定が先に評価される。どちらか一方でも exit 2 ならブロック

## 制約・前提

- **ヘッドレス実行（`claude -p`、CI）でも動作する**。このフックは `permissionDecision: "ask"` を使わず、exit 2 のブロックと additionalContext の案内だけで構成しているため、ユーザーが確認に応答できない環境でも、Claude が Skill ツールで振り分けスキルを読み込めば自力で復旧できる（ブロックされた操作はやり直しになる）
- 判定は「Skill ツールで振り分けスキルが読み込まれたか」であり、その手順に従ったかまでは検証しない（手順の遵守は各 SKILL.md と既存フックの責務）
- フォローアップのプロンプト（「はい」「続けて」）でも原則として宣言が必要。ただし `wip/10_tickets/00_todo/` または `10_doing/` にチケットがある間、または最後のワークのレビュー待ちの間（`workflow-issue-mr-driven` の作業中）は継続条件により宣言不要。`workflow-quick-request` の作業には継続の証拠が無いため、こちらは毎回宣言する（同じスキルの再読込は `already loaded` の 1 行で済み、SKILL.md は再注入されない）
- 継続中に別の依頼を始める場合は、チケットを完了（`20_done`）するか `00_todo` に戻してから振り分けを宣言し直す。レビュー待ちの間に別の依頼を始める場合も、レビューを完了させる（`work-boundary.sh complete`）かチケットを `00_todo` に戻してから宣言し直す。チケットが残っている間、またはレビュー待ちの間は `workflow-guard.sh` / `workflow-boundary.sh` の統制下にある
- サブエージェント（Agent ツール）内のツール呼び出しにもフックが掛かる。親セッションと `session_id` が同じであれば親の宣言が引き継がれる
- 緊急脱出は `WORKFLOW_ENTRY_ENFORCE=0`（このフックのみ）または `WORKFLOW_ENFORCE=0`（ワークフロー系フックすべて）。ユーザーの明示的な指示があるときだけ使う
- 判定ログは `.claude/hooks/workflow.log` に `[entry]` プレフィックスで残る
