# 技術調査の記述規約

技術調査レポートを一貫したスタイルで記述するための規約です。

## 命名規則

ファイル名は次の形式に従います：

```
investigation/<対象技術>-調査.md
```

例：`investigation/Redis-キャッシュ評価.md`、`investigation/GraphQL-API-調査.md`

## 日付フォーマット

- 日付: `YYYY-MM-DD` 形式
- バージョン: セマンティックバージョニング（`v1.2.3` など）

## 結論の3択

調査の結論は必ず以下の3択のいずれかにします：

| 結論 | 意味 | 次のステップ |
|------|------|-------------|
| **採用** | プロジェクトに適しており、導入を推奨 | PoC実施または本番導入のスケジュール決定 |
| **保留** | もう少し調査・検証が必要 | PoCの実施、追加のヒアリング、パイロット導入 |
| **不採用** | プロジェクトに不適切 | 代替案の選定、レポートの共有と理由の説明 |

## 評価基準の定義

### 一般的な評価軸

| 評価軸 | 説明 | 判定の目安 |
|--------|------|-----------|
| **機能性** | 求められる機能を満たしているか | 必須機能の充足率（0〜100%） |
| **パフォーマンス** | 処理速度、スループット、レイテンシ | ベンチマーク結果または目標値との乖離 |
| **メンテナ性** | コードの保守性、テストのしやすさ | コードサンプルの品質、テストカバレッジ |
| **エコシステム** | ドキュメント、コミュニティ、サードパーティ製ツール | ドキュメントの充実度、月間アクティブコントリビューター数 |
| **学習コスト** | 習得に必要な時間と難易度 | 推定学習時間（時間単位）、前提となる知識 |
| **導入コスト** | 初期設定、設定ファイルの変更、統合コスト | 推定工数（人日）、既存コードの変更量 |
| **ライセンス** | ライセンスの種類とビジネスへの影響 | OSSのライセンス種別（MIT, Apache, GPL等） |
| **互換性** | 既存の技術スタックとの互換性 | 依存関係の競合、有無 |

### 評価の付け方

各評価軸は以下のスケールで評価します：

- **◎**: 優秀。この軸の大きな強み
- **○**: 良好。問題なし
- **△**: 課題あり。要改善
- **×**: 不適切。この軸で重大な問題

## 用語の統一

| 用語 | 意味 |
|------|------|
| 調査対象 | 評価する技術・ライブラリ・フレームワーク |
| 代替案 | 調査対象以外の候補となる技術 |
| 結論 | 採用 / 保留 / 不採用のいずれか |
| 契機 | 調査に至ったきっかけ |
| 期待効果 | 導入した場合に期待できる効果 |
| 導入コスト | 初期設定から統合完了までのコスト |
| 学習コスト | チームが習得するために必要なコスト |
| 運用コスト | 本番運用における継続的なコスト |
| 移行コスト | 既存技術から乗り換える際のコスト |

## レポートの構成

レポートは以下の順序で記述します：

1. 概要（結論を先に記載）
2. 背景と動機
3. 評価基準
4. 調査対象の詳細
5. メリットとデメリット
6. 代替案との比較
7. コスト評価
8. 結論と推奨
9. 次回アクション
10. 補足事項

## ベストプラクティス

### 結論は明確に

「どちらとも言えない」は避け、必ず3択のいずれかに絞ります。判断に迷う場合は「保留」とし、追加検証の項目を具体的に記述します。

### 根拠を数値で示す

「速い」「便利」といった主観的な評価は避け、ベンチマーク結果や具体的な事例を根拠に記載します。

### チームの文脈を反映する

評価は自チームの規模、技術スタック、経験を反映して行います。汎用的な評価よりも自チームにとっての適合度が重要です。

### 代替案は最低2つ

一つの技術だけの調査では十分な意思決定ができません。最低2つの候補を比較し、相対的な評価を行います。
