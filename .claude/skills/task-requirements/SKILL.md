# task-requirements — 要件定義書を作成する

要件定義書（ユーザーストーリー・受け入れ基準を含む）を作成する。既存の要件ドキュメントと重複がないか確認した上で、テンプレートに基づいて作成する。

- 要件: `.claude/docs/00_requirements/要件定義書作成.md`
- 仕様: `.claude/docs/10_spec/要件定義書作成.md`

## 手順 0: 既存要件の照合

作成前に、既存の要件ドキュメントと類似するものがないか確認する。

### 既存ドキュメントの検索

ワークスペース内の以下を検索する：

- `requirement/` などのディレクトリにある既存の要件定義書
- プロジェクトのルートの `doc/requirements` 配下のファイル

```bash
find . -name "*.md" | xargs grep -l -i "要件\|ユーザーストーリー\|要求\|requirements" 2>/dev/null
```

### 類似度チェック

見つかった既存ドキュメントについて、以下の観点で類似度を確認する：

- **同じ機能領域**を扱っていないか
- **同じユーザーストーリー**が含まれていないか
- **同じ受け入れ基準**が記載されていないか

類似するものが見つかった場合は、ユーザーに知らせて確認する：

> 既に類似の要件が `XXX.md` に見つかりました。こちらを更新しますか、それとも新規で作成しますか？

- **更新を選択された場合**: 該当のドキュメントを読み込み、ユーザーの指示に従って編集する
- **新規作成を選択された場合**: 手順 1 に進む

### 類似ドキュメントが完全にない場合

テンプレートをコピーして新規作成に進む。

---

## 手順 1: テンプレートの準備

`assets/requirements.template.md` を読み込み、空のテンプレートを新規ファイルにコピーする。

ファイル名はユーザーの要件に応じて決定する（例：`requirement/ログイン機能.md`、`spec/カート購入US.md`）。

---

## 手順 2: テンプレートへの記入（ヒアリング）

テンプレートの各セクションをユーザーの回答に基づいて記入していく。

### 2-1: 概要

- **タイトル**: 要件の名前を決定する
- **背景**: なぜこの要件が必要なのか
- **目的**: この要件で達成したいこと
- **スコープ**: どの範囲を含み、どの範囲を除外するか

### 2-2: ユーザーストーリー

EARS フォーマットの「標準形」を基本に、ユーザーからヒアリングして記入する：

```
As a [ロール]、
I want [やりたいこと]、
So that [理由]。
```

ユーザーの要求を確認し、必要に応じて他のパターン（Now that/In order that、Unless、簡易型）を提案する：

> ユーザーストーリーを EARS フォーマット（As a / I want / So that）で記述します。よろしいですか？

ユーザーが具体的に言及しなかった場合は、以下を順に確認する：

1. **As a（誰が）**: この要件の対象ユーザー/ロールは何か
2. **I want（何を）**: 実現したい機能や行動は何か
3. **So that（なぜ）**: その機能が必要な理由・目的は何か

### 2-3: 受け入れ基準（Acceptance Criteria）

EARS フォーマットの「When / Shall」を基本に、メインフロー・アルタナティブフロー・例外フローの順にヒアリングする：

```
When [イベント]、Shall [システムが満たすべき要件]。
```

**メインフロー（正常系）**を最初に確定する。その後、以下を順に確認する：

1. **メインフロー**: 正常に動作する場合の受け入れ基準
2. **アルタナティブフロー**: 代替的な経路やオプションの受け入れ基準
3. **例外フロー**: エラーケースや例外の受け入れ基準

ユーザーが具体的に言及しなかった場合は、想定されるユースケースから提案する：

> 当該機能の主な流れ（メインフロー）を教えてください。それ以外のパターン（代替経路・エラーケース）も想定して記述します。

### 2-4: 前提条件・制約条件・依存関係・非機能要件

必要に応じてヒアリングし、該当するものを記入する。記入が不要な場合はそのまま空欄としてテンプレートに残す。

---

## 手順 3: 要件定義書の完成と確認

すべてのセクションを記入したら、完成した要件定義書をユーザーに提示して確認を求める。

> 要件定義書を作成しました。以下の内容でよろしければ保存します。

- ファイルパスと内容を表示する
- 修正点があれば、該当するセクションを編集する
- ユーザーが承認したらファイルに保存する

---

## 手順 4: 保存と報告

作成した要件定義書を指定のパスに保存し、ファイルパスと概要を報告する。

> 要件定義書を `[ファイルパス]` に保存しました。

---

## EARS フォーマットのバリエーション早見表

ユーザーが不明な場合は、以下のバリエーションから適切なものを提案する：

| 種別 | フォーマット | 使用場面 |
|------|------------|---------|
| 標準ユーザーストーリー | As a / I want / So that | 機能要件の記述 |
| 理由強調型 | Now that / In order that | 前提条件が重要な場合 |
| 条件付ユーザーストーリー | Unless | 制約や条件を強調する場合 |
| 肯定型 AC | When / Shall | 正常系・実行系の要件 |
| 否定型 AC | When / Shall not | 禁止・制約系の要件 |
| 条件付 AC | If / Then | 分岐・条件処理の要件 |
| 状態遷移型 AC | When / Shall transition to | ステータス遷移を明確にする場合 |
