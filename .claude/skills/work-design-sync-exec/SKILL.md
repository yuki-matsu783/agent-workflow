# work-design-sync-exec — 設計反映実施ワーク

突き合わせ計画書の書き戻し方針に従い、設計反映チケットを順に実施して `docs/` の設計書を実装に合わせる。コードは触らない。

- 要件 / 仕様: `.claude/docs/00_requirements/フェーズ別ワークスキル.md` / `.claude/docs/10_spec/フェーズ別ワークスキル.md`
- チケット運用: `work-ticket-driven` の手順 3・4・5・5.5・6 とエラーハンドリング。本スキルは再掲しない

## 1. 位置づけ

| 項目 | 内容 |
|------|------|
| 前のワーク | `work-design-sync-plan` |
| チケット type | `design-sync`（`docs/**` と `wip/20_plans/**` に書ける。`src/**`・`.claude/**` は書けない） |
| 次のワーク | 通常は振り返り（`work-ticket-driven` 手順 4 の retrospective） |
| ワーク境界 | 設計反映チケットが全部 done になった時点。更新された設計書が人間レビューを受ける |

## 2. 入力

- 突き合わせ計画書 `wip/20_plans/設計反映計画-<slug>.md`（差分一覧・書き戻し方針）
- 設計反映チケット群
- 実装の差分と作業ログ（書き戻す内容の根拠）
- 設計書 `docs/**`

## 3. 成果物とテンプレート

| 成果物 | 作成先 | 備考 |
|--------|--------|------|
| 更新された設計書 | `docs/**`（既存ファイルを Edit） | テンプレートなし。既存の節構成を保ち、レビュー記録に版と変更内容（issue #N）を追記する |
| 差分一覧の更新 | `wip/20_plans/設計反映計画-<slug>.md` | 書き戻した行を「一致」に更新する（証跡） |

## 4. 手順

### 4-1. チケットに着手する

todo 先頭の `0NN-design-sync-…` を `work-ticket-driven` 手順 3 のとおり doing に移してコミットする。

### 4-2. 書き戻す

- 差分一覧の「設計書が古い」「設計に無い決定事項」の行ごとに、該当する設計書の節を Edit する。実装（ファイル・シンボル・テスト）を根拠に書き、推測で埋めない
- 既存の記述は消さず、変更した理由が分かるように書く（例: 「実装時に E004 を追加（`src/auth.ts`）」）
- 要件定義書の受け入れ基準・仕様書のテストシナリオが実際のテストと対応しているか確認し、テスト ID を合わせる
- レビュー記録にバージョンと変更内容を追記する
- 突き合わせ計画書の差分一覧の該当行を「一致」に Edit する
- 「差分なしの確認」チケットの場合は、照合した旨をレビュー記録に 1 行追記する

### 4-3. チケットを完了し、境界を判定する

DoD を確認し、`work-ticket-driven` 手順 5 のとおり done にしてコミットする。`work-boundary.sh status` が `at_boundary: false` なら次の設計反映チケットへ、`true`（`todo_head_type: retrospective`）なら完了報告（更新した設計書と節・残った差分）を返して制御を戻す。

## 5. レビュー観点

- 差分一覧のすべての行が「一致」になっているか。残った差分に理由があるか
- 書き戻した内容が実装と一致しているか（根拠のファイル・シンボル）
- 設計書の既存の記述・構成が壊れていないか。レビュー記録が追記されているか
- 設計書を書き換えることで受け入れ条件が骨抜きになっていないか（実装漏れを設計側で消していないか）

## 6. 次のワークへの引き継ぎ

- 次に読み込まれるスキル: `work-ticket-driven`（retrospective。`todo_head_type: retrospective`）
- 渡すもの: 更新された設計書、差分一覧（全行「一致」）。結果報告の「成果物一覧」に設計書の更新を載せる
- 差し戻し時は呼び出し元が `design-sync` type の追加チケットを起こす

## 7. エラーハンドリング

| 状況 | 対処 |
|------|------|
| 書き戻しの途中でコードの誤りに気付いた | `src/**` には書けない。差分一覧に「実装漏れ」として追記し、呼び出し元に `implementation` の追加チケットを提案する。設計書は実装に合わせて書き換えない |
| `.claude/docs/**` を直したくなった | AI アセットの設計書は `ai-asset-design` フェーズで扱う。`design-sync` では `docs/**` のみ |
| 設計書の記述が実装と両方とも曖昧で、どちらに合わせるべきか決められない | 両案を差分一覧に書き、レビュー観点で人間に判断を仰ぐ。勝手に決めない |

フックの WF001〜WF016 でブロックされたときの対処は `work-ticket-driven` のエラーハンドリングに従う。
