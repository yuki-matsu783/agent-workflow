# work-design-sync-plan — 設計反映計画ワーク

実装の結果と設計書の**差分を洗い出し**、何をどこに書き戻すかを決め、設計反映チケット群と次の計画チケットを起こす。設計書は直さない。

- 要件 / 仕様: `.claude/docs/00_requirements/フェーズ別ワークスキル.md` / `.claude/docs/10_spec/フェーズ別ワークスキル.md`
- チケット運用: `work-ticket-driven` の手順 3・5・5.5・6 とエラーハンドリング。本スキルは再掲しない

## 1. 位置づけ

| 項目 | 内容 |
|------|------|
| 前のワーク | `work-implementation-exec` |
| チケット type | `design-sync-plan`（`wip/20_plans/**` に書ける） |
| 次のワーク | `work-design-sync-exec`（type `design-sync`） |
| ワーク境界 | 計画チケットが done になった時点。突き合わせ結果（差分一覧と書き戻し方針）が人間レビューを受ける |

## 2. 入力

- 実装の差分（実装ワーク開始コミット〜HEAD の `git diff`、`git log`）
- 実装チケットの作業ログ「仕様からの逸脱」
- 設計書 `docs/**`（要件定義書・仕様書）と設計計画書
- 全体計画（受け入れ条件との対応）

## 3. 成果物とテンプレート

| 成果物 | 作成先 | テンプレート |
|--------|--------|-------------|
| 突き合わせ計画書 | `wip/20_plans/設計反映計画-<slug>.md` | `work-ticket-driven/assets/plan.template.md`。「調査サマリ」を**差分一覧**（実装 × 設計書の対応表）に、「変更対象ファイル」を書き戻す設計書と節に、「実装ステップ」を設計反映チケットの一覧に使う |
| 設計反映チケット群 | `wip/10_tickets/00_todo/0NN-design-sync-<slug>.md`（1 枚以上。差分が無ければ「差分なしの確認」1 枚） | `work-ticket-driven/assets/ticket.template.md` |
| 次の計画チケット | 通常 `0NN-retrospective-振り返り.md`（設計反映はフェーズ列の最後） | 同上 |

## 4. 手順

### 4-1. 着手する

todo 先頭の `0NN-design-sync-plan-…` を `work-ticket-driven` 手順 3 のとおり doing に移してコミットする。

### 4-2. 突き合わせる

読み取りだけで次を作る:

- **差分一覧**: 設計書の節（インターフェース・処理フロー・エラー・テストシナリオ・受け入れ基準）ごとに、実装（ファイル・シンボル・テスト）と照合し、次のどれかに分類する
  - 一致（書き戻し不要）
  - 実装が正しく設計書が古い → 設計書を直す
  - 設計書が正しく実装が漏れている → **設計反映では直さない**。呼び出し元に `implementation` の追加チケットを提案し、レビュー観点に書く
  - 設計に無い決定事項（実装中に決めた挙動・エラーコード・制約） → 設計書に追記する
- **書き戻し方針**: 設計書ごとに、直す節・追記する内容・レビュー記録に書く版と変更内容
- **受け入れ条件の確認**: 受け入れ条件がテストと設計書の両方で裏付けられているか

### 4-3. チケットを起こす

1. 設計反映チケット群（`type: design-sync`）。1 チケット = 1 設計書。DoD の型:
   ```markdown
   - [ ] docs/<path> の <節> が実装（<ファイル・シンボル>）と一致するよう更新されている
   - [ ] 設計に無かった決定事項 <X> が追記されている
   - [ ] レビュー記録に版と変更内容（issue #N）が追記されている
   - [ ] 差分一覧の該当行が「一致」になっている
   ```
   差分が無い場合も「差分なしを確認し、レビュー記録に確認した旨を追記する」チケットを 1 枚起こす（設計と実装が一致していることの証跡）
2. 次の計画チケット: フェーズ列の次（通常は振り返り `type: retrospective`）

### 4-4. 完了する

計画チケットの DoD を確認し、`work-ticket-driven` 手順 5 のとおり done にしてコミットし、`work-boundary.sh status` で `at_boundary: true`・`todo_head_type: design-sync` を確認して完了報告を返す。

計画チケットの DoD の型:

```markdown
- [ ] wip/20_plans/設計反映計画-<slug>.md に差分一覧（分類つき）と書き戻し方針が書かれている
- [ ] 実装漏れ（設計書が正しく実装が無い）があれば一覧化され、レビュー観点に書かれている
- [ ] 設計反映チケット N 枚と次の計画チケット（通常は振り返り）が todo に起票されている
```

## 5. レビュー観点

- 差分一覧が設計書の全節を照合しているか（照合漏れの節がないか）
- 「設計書が古い」と「実装が漏れている」の分類が正しいか（実装を正として設計書を書き換えてよい差分か）
- 設計に無い決定事項が拾われているか（作業ログの逸脱一覧と一致するか）
- 実装漏れがある場合、その扱い（追加チケット / 今回はスコープ外）

## 6. 次のワークへの引き継ぎ

- 次に読み込まれるスキル: `work-design-sync-exec`
- 渡すもの: 突き合わせ計画書（差分一覧・書き戻し方針）と設計反映チケット群
- 差し戻し時は呼び出し元が `design-sync-plan` type の追加チケットを起こす

## 7. エラーハンドリング

| 状況 | 対処 |
|------|------|
| `docs/**` へ書こうとして WF009 が出た | 計画ワークでは設計書を直さない。設計反映チケットで直す |
| 実装が漏れている差分が多い | 設計反映ではなく実装の問題。呼び出し元に `implementation` の追加チケットを提案し、本ワークはその旨を計画書とレビュー観点に書いて完了する |
| 設計書が無い（設計を省略した） | 全体計画で設計反映も省略すべきだったケース。差分なし確認の代わりに「設計書が無い」旨をレビュー観点に書き、振り返りチケットを起こして完了する |

フックの WF001〜WF016 でブロックされたときの対処は `work-ticket-driven` のエラーハンドリングに従う。
