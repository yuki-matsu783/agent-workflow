# WF012 引用符内状態ファイル名誤反応の修正計画

- 作成元チケット: 001-investigation-WF012原因調査.md
- 作成日: 2026-08-30

## 調査サマリ

- `workflow-boundary.sh` 58〜73行目の (a)(b) レビュー状態ファイル保護ブロックは、Bash コマンドを `&&`/`||`/`;`/`|` でセグメント分割した後、各セグメントの**生の文字列**に対して `case "${seg}" in *review-state.json*)` で判定している（67行目）
- そのため `gh issue create --title "review-state.json の扱い" --body x` のように、引用符内の文字列に `review-state.json` が含まれるだけのコマンドも誤ってマッチし、WF012 でブロックされる（issue #29 の再現手順）
- 一方 `workflow-guard.sh` の `check_bash`（194〜268行目）は、セグメント分割の**前**にコマンド全体をサニタイズしている: `sanitized=$(printf '%s' "${COMMAND}" | sed -E "s/'[^']*'/QUOTED/g; s/\"[^\"]*\"/QUOTED/g")`（198行目）。クォート内文字列を丸ごと `QUOTED` に置き換えることで、クォート内の任意の文字列による誤マッチを防いでいる
- `workflow-boundary.sh` に同じサニタイズを単純適用すると、`rm "wip/10_tickets/review-state.json"` のようにパスそのものをクォートしたコマンドが `rm QUOTED` に変換され、`review-state.json` という文字列が消えてしまう。これは issue #29 の受け入れ条件（`rm "wip/10_tickets/review-state.json"` は引き続き WF012）に反する
- `workflow-guard.sh` 側にも同種の「クォートされたパスは検証できない」問題があり、`wf_validate_mv()`（155〜172行目）は `QUOTED` トークンを見つけたら即座に「検証不能」として拒否している（160行目: `QUOTED) return 1 ;;`）。ただしこれは mv 系コマンド専用の「パスは引用符なしで書け」という制約であり、`--title` のような無関係な引数までブロックしてしまうため WF012 にはそのまま転用できない
- `.claude/skills/work-ticket-driven/scripts/test-hooks.sh` に既存の WF012 テスト（TC025・TC025-w・TC025-doing・TC025b・TC025c、414〜508行目付近）があり、`BOUNDARY="${HOOKS_DIR}/workflow-boundary.sh"` を `bash_json` で組み立てた JSON を渡して `run_boundary` で実行する既存ヘルパーがそのまま使える

## 変更方針

`workflow-boundary.sh` の (a)(b) ブロックを次の二段判定に変更する。

1. **クォート外パス判定**: セグメントごとに `sanitized`（クォート→`QUOTED` 置換、`workflow-guard.sh` と同じ sed）を作る。`READONLY_RE` / `SCRIPT_RE` の除外判定も `sanitized` に対して行う（元は未サニタイズの `seg` に対して行っていたが、判定対象を統一する。コマンド名の判定なのでクォートの有無で結果は変わらず、安全な変更）。`sanitized` に `*review-state.json*` が含まれれば WF012
2. **クォート内パス判定**: 1 でヒットしなければ、新規関数 `wf_quoted_targets_state()` で元の `seg` からクォート文字列を `grep -oE "'[^']*'|\"[^\"]*\""` で抽出し、各値の前後のクォート記号を取り除いた上で `review-state.json` と完全一致、または `*/review-state.json` に一致するか判定する。一致すれば WF012

この方式なら、クォート内の値が「パスそのもの」の場合だけ検出し、他の文字列と混在する場合（`review-state.json の扱い` のように末尾に別の文字列が続く）は無視できる。mv 専用の `wf_validate_mv` のような「クォートを一律拒否」方式は、`--title` のような無関係な引数を巻き込むため不採用。

### 代替案（不採用）

- **クォート内にパスがあれば無条件で検証不能として拒否**（`wf_validate_mv` 方式の単純転用）: `gh issue create --title "review-state.json の扱い"` のような正当なコマンドまでブロックしてしまい、受け入れ条件1に反するため不採用

## 実装ステップ

1. `workflow-boundary.sh` に `wf_quoted_targets_state()` を追加する:
   ```bash
   # クォート内の値がレビュー状態ファイルのパスそのものかどうかを判定する。
   # 例: "wip/10_tickets/review-state.json" や 'review-state.json' は該当。
   # "review-state.json の扱い" のように他の文字列と混在する場合は非該当（パスとして使われていない）
   wf_quoted_targets_state() {
       local seg="$1" q val
       while IFS= read -r q; do
           [ -z "${q}" ] && continue
           val="${q:1:-1}"
           case "${val}" in
               review-state.json|*/review-state.json) return 0 ;;
           esac
       done < <(printf '%s' "${seg}" | grep -oE "'[^']*'|\"[^\"]*\"")
       return 1
   }
   ```
2. Bash ケースのループ本体を書き換える:
   ```bash
   Bash)
       while IFS= read -r seg; do
           seg=$(printf '%s' "${seg}" | sed -E 's/^[[:space:]]+//; s/[[:space:]]+$//')
           [ -z "${seg}" ] && continue

           sanitized=$(printf '%s' "${seg}" | sed -E "s/'[^']*'/QUOTED/g; s/\"[^\"]*\"/QUOTED/g")
           printf '%s' "${sanitized}" | grep -Eq "${READONLY_RE}" && continue
           printf '%s' "${sanitized}" | grep -Eq "${SCRIPT_RE}" && continue

           case "${sanitized}" in *review-state.json*) wf012 "${COMMAND:0:200}" ;; esac
           wf_quoted_targets_state "${seg}" && wf012 "${COMMAND:0:200}"
       done <<<"$(printf '%s' "${COMMAND}" | sed -E 's/\|\||&&|;|\|/\n/g')"
       ;;
   ```
3. `test-hooks.sh` の TC025 系に以下を追加する（`run_boundary "$(bash_json "...")"` + `check` の組み合わせ。関数は既存のものをそのまま使う）:
   - `gh issue create --title "review-state.json の扱い" --body x` → exit 0（WF が出ない）
   - `rm "wip/10_tickets/review-state.json"` → exit 2, "WF012"
   - `echo x > "wip/10_tickets/review-state.json"` → exit 2, "WF012"（クォート版のリダイレクトも念のため確認）
   - 既存の TC025b（クォート無し版）・TC025c（読み取り系）は変更せずそのまま残す
