## うまくいかなかったこと

- **`gh` CLI が使えない環境制約**: このリモート実行環境では `gh` の GraphQL API 呼び出し（`gh pr comment` / `gh pr view` 等が内部で使用）がエージェントプロキシのポリシーにより拒否される（REST の `gh api` は動く）。`work-boundary.sh request` / `complete` は `gh pr comment` に依存しているため通常モードでは動作せず、`--local` オプションでの自己レビュー相当の運用に切り替えた。ユーザーに事前確認のうえで実施した
- **`wb_compute` のワーク境界誤判定**: `wip/10_tickets/20_done/` のチケット番号は「実施順の連番」だが、境界判定（`workflow-boundary.sh`）は 20_done 内の**最大番号**のチケットを「直前の done」とみなす。前回マージ済み PR（#37/#38）が完了処理（`merge-prep.sh reset-wip`）を経ずにマージされ、`029-retrospective-振り返り.md` が review-state なしで main に残っていたため、今回新設した `001`〜`003` の番号がすべて 29 未満となり、`002`（ai-asset-implementation）完了時の本来のワーク境界を自動検知できなかった（`003`(retrospective) の type が 029 の type と一致してしまい `at_boundary=false` と誤判定）。AskUserQuestion による手動チェックポイントで代替した
- Bash の `bash_groups` が `ai-asset-implementation` では `test` のみのため、`python3 -m json.tool` 等での機械的な JSON パース確認ができず、Read ツールでの目視確認に留めた

## 改善提案

1. **`gh` の GraphQL 依存の解消**（恒久的な教訓・CLAUDE.md/フックの改訂候補）: `work-boundary.sh` / `merge-prep.sh` の `gh pr comment` / `gh pr view` 呼び出しを、プロキシが許可する REST（`gh api repos/{owner}/{repo}/issues/{n}/comments` 等）に置き換えるか、GitHub MCP サーバーツール（`mcp__github__*`）を使う経路を用意すると、GraphQL が制限された実行環境でも通常モードのレビュー往復が機能する。issue 化を推奨
2. **`reset-wip` 未実施のまま merge されたブランチ対策**: 完了処理（`merge-prep.sh reset-wip` 等）を経ずに `wip/` 付きでマージされた履歴があると、後続の全ワークフローでワーク境界判定が誤動作し得ることが今回判明した。`workflow-issue-mr-driven` 手順 6（完了処理）を必ず通す運用の徹底に加え、`wb_compute` を「20_done の最大番号」ではなく「現在のブランチで新規に作成されたチケットの中の最新」に限定するなど、境界判定ロジック自体の改善を issue 化することを提案する
3. `ai-asset-implementation` の `bash_groups` に軽量な検証コマンド（`python3 -c` での JSON/YAML 構文チェック等）を許可するか検討する

## 残課題・フォローアップ

- 上記改善提案 1・2 は今回のスコープ外（issue #4 は文言明記のみが対象）のため、別 issue 化をユーザーに提案する
- `wip/10_tickets/20_done/` に残る旧 PR（#37/#38 以前）のチケット群は、いずれかのタイミングで `merge-prep.sh reset-wip` 相当のクリーンアップが必要
