## うまくいったこと

- 実装前に Explore/Plan エージェントで影響範囲を調査させたことで、`wf_validate_mv` の制約（`.claude/skills/**` の `git mv` がブロックされる）を実装前に把握でき、対応をチケット計画に織り込めた
- 主要な設計分岐（3層分類の粒度、`ticket-driven-workflow` の分解方法、`git mv` 制約への対処）を `AskUserQuestion` でユーザーに確認してから進めたため、実装フェーズでの手戻りがほぼ無かった
- チケットを細かく分割していたため、004完了後に発覚した「`ai-asset-implementation` type は `.claude/docs/**` を触れない」というギャップにも、チケット挿入・番号繰り下げで柔軟に対応できた
- 006 の横断 grep で、`task-ai-asset-creator/scripts/init-asset.sh` の `TEMPLATE_DIR` が旧パス参照のままという実害あるバグを発見・修正できた（`name:` や見出しの機械的置換だけでは見逃していた）

## うまくいかなかったこと

- 事前調査の時点で `ai-asset-design` と `ai-asset-implementation` の担当パスの違い（`.claude/docs/**` は前者専用）を見落としており、004完了後に気づいて計画変更（005の追加）が必要になった
- 作業中に2回、身に覚えのない外部変更を検知した：(1) `refactor/7-skill-taxonomy-layers` からの操作後、無関係な `feature/9-default-branch-check` ブランチにHEADが切り替わっていた（`ListAgents` で確認したところ、同一マシン上に並行実行中のクラウドセッションが複数存在した）、(2) `.gitignore` に身に覚えのない追記（ユーザー確認の上「受け入れてOK」として許容）。並行して動く他セッションとワークツリーを共有する環境固有のリスクとして記録する
- `workflow-guard.sh` の `READONLY_RE` に `echo` が含まれておらず、`ls ... 2>/dev/null` のような複合コマンドでの確認が度々ブロックされた（Glob/Readで代替。以前の振り返りでも同じ指摘が出ている累積課題）
- `git mv ... && git add ... && git commit ...` のような複合コマンドが `wf_validate_add` の `-A` フラグ拒否で一括実行できず、毎回コマンドを分割する手間が発生した

## 改善提案

- **敵対的レビューエージェントの自動起動**（ワーク完了チェックポイント）の実装は今回スコープ外とした。次段階のissueとして起票することを提案する
- **`READONLY_RE` への `echo` 追加**: 過去の振り返り（`wip/30_reports/結果報告-入口ガード継続とwip構成統一.md`）でも同じ改善候補が挙がっており、累積している。次回の `ai-asset-implementation` チケットでまとめて対応することを提案する
- **チケット分割時の担当パスチェックリスト化**: `ai-asset-design`（`.claude/docs/**`）と `ai-asset-implementation`（`.claude/hooks/**`・`.claude/rules/**`・`.claude/skills/**`）の境界を、チケット作成時点で影響ファイル一覧と突き合わせるチェックリストを `work-ticket-driven` の手順2に追加すると、今回のような手戻りを防げる
- **`wf_validate_add` の `-A` フラグ**: `git add -A` のような一般的なフラグの扱いを見直すか、`work-ticket-driven` の SKILL.md に「個別パス指定が必要」と明記して迷いを減らす
