## うまくいかなかったこと

- 当初の全体計画では `.claude/docs/10_spec/ワークフロー入口ガード.md` を `ワークフロー振り分け実施済み判定.md` に `git mv` でリネームする想定だったが、チケット駆動フックの Bash allowlist が `.claude/docs/**` に対する `mv`/`git mv`/`git rm` を許可しておらず（`mv` 系は `wip/10_tickets/` 配下同士か `ai-asset-implementation` タイプでの `.claude/skills/` 配下移動のみ許可）、実行時にブロックされた。GitHub API（`create_or_update_file`/`delete_file`）経由での回避はフックの意図を迂回することになるため行わず、ファイル名は `ワークフロー入口ガード.md` のまま据え置き、内容（タイトル・本文）のみ更新する方針に変更した
- 結果として、ドキュメント内のタイトルは「振り分け実施済み判定」だが、ファイルパスは旧称のままという不一致が残っている。他ドキュメントからの参照箇所には「ファイル名は旧称のまま据え置き」という注記を添えて説明した

## 改善提案

- `.claude/hooks/workflow-types.json` の Bash allowlist に、`ai-asset-design` タイプでも `.claude/docs/**` 配下限定の `git mv` を許可する項目を追加することを検討候補として提案する。ドキュメントの改名・再編は今後も発生しうるため、design チケットの範囲内で完結できるようにする価値がある
- 上記の改善は「フックのロジック変更」に当たり振る舞いが変わるため、対応する場合は `workflow-issue-mr-driven` で新規 issue 化して進める

### 使った AI アセットの振り返り（workflow-quick-request 手順5相当）

| 種類 | 気付き |
|------|--------|
| スキル `workflow-quick-request` | 問題なし。用語相談を軽作業として適切に開始でき、規模超過を検知して `workflow-issue-mr-driven` への切り替えを促す判定も機能した |
| スキル `workflow-issue-mr-driven` | 問題なし。issue/PR/チケット駆動の一連の流れがスムーズに進んだ |
| スキル `work-ticket-driven` | **足りなかった**: `.claude/docs/**` を触る `ai-asset-design` タイプでファイル名変更（`git mv`/`git rm`）ができないことが、実際に手を動かすまで分からなかった。`references/permission-matrix.md` の Bash allowlist 表に「ドキュメントの改名はできない」旨を明記しておくと、計画段階で見送りを織り込めた |
| フック `workflow-entry.sh` / `workflow-guard.sh` | 想定どおり機能した。文言変更のみでロジックは無変更、テストも全PASS |
| CLAUDE.md | 「作業の振り分け」への更新は`session_memory.file_level`のask経由で問題なく編集できた |
