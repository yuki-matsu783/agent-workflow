## うまくいかなかったこと

- **チケット番号の衝突**: `wip/10_tickets/20_done/` には過去の PR（#12 系、014 まで）が残っており、当初 001 から振ったチケットが `work-boundary.sh` の「最後の done」判定（ファイル名先頭の連番の最大値）で過去の無関係なチケット（014）を指してしまうことに、001 を done にした直後の `work-boundary.sh status` で気づいた。連番を 015〜017 に振り直して対処した。チケット作成時点で `wip/10_tickets/20_done/` の既存最大連番を確認する手順が `work-ticket-driven` の手順2に無いため、改善提案に記載する
- **`gh` CLI が使えない環境**: このセッションの実行環境には `gh` CLI が無く、GitHub 操作は MCP ツール（`mcp__github__*`）経由に限定されていた。`work-boundary.sh request` / `complete`（非 `--local`）は内部で `gh pr comment` / `gh pr view` を呼ぶため実行できず、`--local` モードで代替した。実際のレビューコメントは `mcp__github__add_issue_comment` で個別に投稿し、レビュー状態の記録だけ `work-boundary.sh --local` で行った。人間による実際の GitHub レビューは経由していない（セルフレビューのみ）

## 改善提案

- `work-ticket-driven` の手順2（チケット作成）に「`wip/10_tickets/20_done/` の既存チケットの最大連番を確認し、その次の番号から振る」旨を明記する。現状は「NNN は実施順の連番」としか書かれておらず、`wip/10_tickets/` が過去の PR から引き継がれる構成（done チケットを削除しない運用）だと今回のような衝突が起きうる
- `workflow-issue-mr-driven` に、実行環境に `gh` CLI が無い場合の代替手順（本レポートで採った「MCP でコメント投稿 + `work-boundary.sh --local` で状態記録」）を明記するか、`work-boundary.sh` 自体に gh 呼び出し失敗時のフォールバックを設けることを検討する。ただし本 issue #28 のスコープ外（`work-boundary.sh` / `workflow-boundary.sh` の変更は見送り）のため、別 issue として提案する

## 残課題・フォローアップ

- 上記「改善提案」の2点（チケット採番の重複回避手順の明記、`gh` 不在環境への対応）は、ユーザーの判断でスキル改訂や別 issue 化を検討してもらう
- 本 PR は `gh` CLI 不在によりセルフレビューのみで進行した。人間による実際の GitHub レビューは PR #32 上で改めて行うことができる
