## うまくいかなかったこと

- チケット002（現016）の type を最初 `implementation` にしてしまい、`.claude/hooks/**` への Edit が WF002（保護パス）でブロックされた。doing チケットの type は書き換え不可（WF008）のため、一度 todo に戻して type を `ai-asset-implementation` に修正してから再着手する手戻りが発生した
- 新規チケットの連番を 001 から振ってしまい、既存の done チケット（issue #12 対応分、001〜014）と重複した。`work-boundary.sh status` の `last_done` 判定はファイル名先頭の連番の最大値で done チケットを特定する仕組みのため、番号が重複すると誤ったチケットを「直前の完了」として参照してしまう（実際に `at_boundary` の判定が一時的に不正確になった）。015〜017 に振り直して解消した
- このセッション環境では `gh` CLI の直接利用がブロックされており（GitHub access is not enabled for this session エラー。GitHub MCP サーバー経由のみ許可）、`work-boundary.sh` の通常の `request` / `complete`（内部で `gh pr view` 等を呼ぶ）が `[WF013]` で失敗した。`--local` フラグで代替し、GitHub 側へのレビュー依頼コメントは `mcp__github__add_issue_comment` で代わりに投稿した。ただし `complete --local` は実際の承認状態（APPROVED/CHANGES_REQUESTED）やインラインコメントの自動チェックを行わないため、性善説の運用になる

## 改善提案

- **チケット番号の採番ルールを明文化する**: `work-ticket-driven` の手順2には「NNN は実施順の連番」とあるが、これが「そのワークフロー内での連番」なのか「`wip/10_tickets/20_done/` 全体を通した連番」なのかが曖昧だった。`work-boundary.sh` の `last_done` 判定がファイル名の数値最大値に依存する実装である以上、後者（全体通し連番）を明記し、チケット作成前に `ls wip/10_tickets/20_done/ | sort` 等で既存最大値を確認する手順を追加すべき
- **gh CLI が使えない実行環境向けの経路をドキュメント化する**: `workflow-issue-mr-driven` / `work-ticket-driven` は `gh` CLI の直接利用を前提にしているが、GitHub MCP サーバー経由でのみ GitHub 操作が許可される実行環境（本セッションなど）では `request` / `complete`（非local）が原理的に動作しない。`--local` + MCP ツールでのコメント投稿を正式な代替経路として明記し、`complete --local` が承認状態を自動チェックしない旨の注意も添えるとよい

## 残課題・フォローアップ

- `complete --local` を使ったため、実際の GitHub 上のレビュー承認・インラインコメントの自動反映は行われていない。マージ前に人間が PR #34 のコメント・レビューを直接確認することを推奨する
- gh CLI 直接利用がブロックされる実行環境向けのドキュメント整備は、本 issue のスコープ外として今回は着手していない。別 issue として起票するかはユーザー判断とする
