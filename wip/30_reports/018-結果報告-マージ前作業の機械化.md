## うまくいったこと

- `work-boundary.sh` / `review-state.json` / `workflow-boundary.sh` の型（スクリプトだけが書く・実操作を自ら行って証跡を残す・フックが迂回を exit 2 で拒否）をそのまま `merge-prep.sh` / `merge-prep.json` / WF015 に写せたため、設計の新規部分は「reset → check → notify → ready の順序」「`ready` の再検証」「承認⑤⑥」に絞れた
- 参考リポジトリの判断（DDR i0028-01: 片付けはスクリプト化しコミットは含めない / i0046-01: 衝突検知は `merge-tree` で機構化 / i0086-01: issue 通知は投稿前に人間承認 / i0112-01: 片付けの位置）を、本リポジトリの前提（`reset-wip` が即コミットする）に合わせて取捨選択し、理由を仕様と全体計画に残した
- 衝突判定のテストは `gh` をモックしつつ `git merge-tree` は bare リモートの `base` ブランチで実物を通し、「衝突あり → `git merge` で解消 → 衝突なし」の往復まで検証できた（実装初回で 187/189、失敗はモックの引数位置ミスのみ）
- ワーク 1・2 とも人間レビューで指摘 0 件。仕様（015）を先に固めてから実装（016+017）した順序が効いた

## うまくいかなかったこと

- Bash ツールで `2>&1` を付けたテスト実行がリダイレクト判定で WF003 になった。#13 の残課題「Bash ツールで `2>&1` を付けない」が CLAUDE.md / スキルに未反映のまま再発した
- `jq`（JSON の妥当性確認）と `bash -n`（構文チェック）がチケット作業中の Bash allowlist に無く、`ai-asset-implementation` でも実行できない。テストの実行と done 後の確認で代替した
- 用語辞書の「ワーク完了チェックポイント」が #12 の改訂（承認者＝人間）を取りこぼしていたのを今回ついでに直した。用語辞書は仕様変更時の更新対象として見落とされやすい
- `gh pr ready` を常時拒否にしたため、`task-gh-feature` を単独で使う場合も直接 ready にできなくなった（同スキルに注記）。単独用途を重視するなら緩和の検討が要る
