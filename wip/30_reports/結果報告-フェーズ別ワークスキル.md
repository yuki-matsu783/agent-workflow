## うまくいったこと

- **境界判定の機械化を前提にできた**: 「計画と実施を別 type にすれば `work-boundary.sh` の既存規則だけで計画→実施→計画のレビューが入る」ことを要件に固定し、フック本体を一切変えずに済んだ。type 定義の追加（JSON）とテストだけで実現
- **`todo_head_type` → スキルの一意対応**: 呼び出し元は目視で type を比べず、`status` の出力からスキルを決める。これが「計画 type をフェーズごとに分ける」判断の決め手になり、レビュー依頼やチケット名からもフェーズが読める
- **連鎖方式**: 全体計画は最初の計画チケットだけ起こし、各計画ワークが実施チケット群 + 次の計画チケットを起こす。連番が単調増加し、起こし忘れは計画ワークの DoD と「呼び出し元が直接起こせる」リカバリで押さえた
- **SKILL.md の型を先に 1 件で確定**（`work-overall-plan`）してから 12 件を量産したので、構成のぶれが無い。チケット運用の手順は `work-ticket-driven` の手順番号で参照し、13 スキルは薄く保てた
- **この issue 自身が AI アセットのフェーズ列の実例**になった（`ai-asset-design` → `ai-asset-implementation` → `retrospective`）。踏んだ制約（リダイレクト付きテスト実行の拒否、`.claude/docs/` を実装中に直せない、`CLAUDE.md` は `allowed_paths` が要る）を `work-ai-asset-*` の evals に落とせた
- 各ワークのレビューで指摘 0 件（設計の判断 4 点をレビュー依頼に明示して先に確認を取ったため）

## うまくいかなかったこと

- **Grep ツールの `glob` の空振り**: `work-*/SKILL.md` では 0 件になり（`**/work-*/SKILL.md` が必要）、005〜007 のプレースホルダ検査が実は何も検査していなかった。008 で再検査して問題なしと確認したが、検査手段自体の検証を怠った
- **Bash の複合コマンド**: チケット着手直後に `ls; echo; cat` や `git mv … && git log && work-boundary.sh status` を 1 行にまとめて WF003 で弾かれた（読み取り系単体・チケット運用コマンド以外は doing 中に使えない）。`bash tests/x.sh 2>&1 | tail` もリダイレクト禁止で拒否
- **jq が allowlist 外**で、編集した JSON の妥当性を直接確認できなかった。代わりに `test-json-syntax.sh` を新設して `test` グループで実行した（結果として恒久的なテストになったが、仕様書のテストシナリオには無い追加分）
- **実装中に仕様書を直せない**（`ai-asset-implementation` は `.claude/docs/**` deny）。`test-json-syntax.sh` の TC 追記を設計文書に反映できず、本報告の改善提案に回した。設計→実装の分離の代償で、同 issue 内で仕様の不備に気付いたときの経路（`ai-asset-design` の追加チケット → type が交互になりレビュー往復が増える）は重い
- `docs/` の構成（`00_requirements` / `10_spec`）はリポジトリに実体が無く「推奨」止まり。実プロジェクトで最初に使うときに決める必要がある
